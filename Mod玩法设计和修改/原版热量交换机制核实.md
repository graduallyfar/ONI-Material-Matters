# 原版热量交换机制核实

本文件记录从**本机安装的游戏**（Steam `E:\SteamLibrary\steamapps\common\OxygenNotIncluded`，Steam buildid `24423041`，`SimDLL` 里的 Klei 构建号 `707956`）核实到的原版热量交换算法，供 Mod 设计判断材料属性该从哪里接入。只记录原版事实，不代替玩法设计。

## 0. 依据与核实方式

| 来源 | 用途 | 位置 |
| --- | --- | --- |
| `Assembly-CSharp.decompiled.cs` | C# 侧接口、单位、注热入口 | `E:\ONI-Ref\Assembly-CSharp\Assembly-CSharp.decompiled.cs`（行号见各节） |
| `SimDLL.dll` + `SimDLL.pdb` | 原生传导内核真实公式与常量 | `OxygenNotIncluded_Data\Plugins\x86_64\`（PDB 带完整函数名与局部变量名） |
| `elements\*.yaml` | 元素物性数据（SHC、导热系数、三个接触面积倍率） | `OxygenNotIncluded_Data\StreamingAssets\elements\` |

原生部分的做法：解析 PDB 的 MSF/DBI 流取出函数符号地址，再用 `objdump -d -M intel` 反汇编对应区间，读浮点常量与算式。本文中标注地址的结论均由反汇编直接读出。

**注意**：C# 引用来自 `E:\ONI-Ref` 的反编译版本，未与安装目录 `Assembly-CSharp.dll` 逐字节比对；原生公式与数据来自安装目录当前版本，是本文最硬的部分。

## 1. 单位与时间步

- 温度：°C；质量：kg（`PrimaryElement.Mass`）；比热容 SHC 单位 DTU/(g·°C)。
- 热容 `C = mass(kg) × SHC`，单位 kJ/°C（`GameUtil.GetEnergyInPrimaryElement` = `0.001f * (T × mass*1000 × SHC)`，行 281555）。
- 注热接口用 kJ；建筑产热用 kW（`SelfHeatKilowattsWhenActive` / `ExhaustKilowattsWhenActive`）。
- 单元格温度更新在原生 `UpdateTemperature` 内写死 **0.2 s** 步长（`0x180036976` 处加载 double 常量 0.2）；C# 侧 `Sim200ms` 同为 5 Hz。

## 2. 单元格 ↔ 单元格（原生，主要传导通道）

符号与地址：`UpdateTemperature` `0x180036470`（1636 B），`details::CalculateTemperatureExchange_precise` `0x180035670`，`CalculateTemperatureExchange`（float 包装）`0x180035590`，`ElementTemperatureData::GetSurfaceAreaMultiplier` `0x1800361f0`，`CellSOA::GetInsulationValue` `0x1800361b0`。

对相邻两格 a、b：

```
C_i   = mass_i × SHC(元素_i)
ΔT    = T_hot − T_cold
K     = 两格 insulation 均为 255(1.0) 时  sqrt(k_a × k_b)
        否则                             min( k_a × (ins_a/255)² , k_b × (ins_b/255)² )
A     = SurfaceAreaMultiplier(元素_a, 相态_b) × SurfaceAreaMultiplier(元素_b, 相态_a)
E     = K × A
Q     = min( ΔT × E × 0.2 , 0.25 × ΔT × C_cold , 0.25 × ΔT × C_hot )     // 0.2 = 时间步(s)
T_eq  = (T_a·C_a + T_b·C_b) / (C_a + C_b)
T_cold' = min(T_cold + Q / C_cold, T_eq)
T_hot'  = max(T_hot  − Q / C_hot , T_eq)
最终两格温度统一 clamp 到 [1, 10000]
```

要点：

- 几何平均那支不是直接开方，而是 `exp(0.5 × (log a + log b))`（调用 `logf`/`expf`，`0x1800a3230` / `0x1800a2f80`），数学等价于 √(k_a·k_b)。
- **两个 0.25 是热容限幅**（每步最多移动「把该格推到对侧温度所需能量」的 1/4），配合 `T_eq` 钳制，避免振荡。格子越重（C 越大）越不容易被瞬时拉平。
- 相态由 `元素state & 3` 决定：`1`→固、`2`→液、`3`→气，取的是**对方相态**对应的本元素倍率（`GetSurfaceAreaMultiplier(this, other)`）。
- `insulation` 是每格的字节，默认 255（`Sim.Cell.SetValues`，行 419689）；`SimMessages.SetInsulation(cell, value)`（行 421915）由瓦片写入，瓦片写 `def.ThermalConductivity`、非瓦片写 1.0（行 294731、294736）。所以**只要有任何一格被瓦片改过 insulation，就落进 min 支**：保温砖 `0.01` → `(0.01)² = 1e-4` 量级的系数。
- 气压/质量不影响 K，只通过 C 影响限幅。
- 空气-固体接触面积倍率很大，见下节数据。

### 2.1 接触面积倍率（元素数据，实测摘录）

数据文件 `StreamingAssets\elements\{solid,liquid,gas}.yaml`，字段 `solidSurfaceAreaMultiplier` / `liquidSurfaceAreaMultiplier` / `gasSurfaceAreaMultiplier` 表示「本元素接触对方某相态时的面积倍率」。

- 全部气体：`solid=25, liquid=1, gas=1`
- 全部液体：`solid=1, liquid=25, gas=1`
- 绝大多数固体：`1,1,1`；例外：`Snow/CrushedIce/StableSnow` 为 `1,1,1000`，`TempConductorSolid` 全为 `2`，`Unobtanium`、`Vacuum`、`Void`、`COMPOSITION` 全为 `0`
- 值分布（212 个元素，共 636 个字段）：`1`×534、`25`×84、`0`×12、`1000`×3、`2`×3

由此：气↔固 = 25×1 = 25；液↔液 = 25×25 = 625；固↔固 = 1；雪↔气 = 1000×25 = 25000（雪因此快速吸热融化）。

### 2.2 同族公式

- `UpdateTemperatureForBackwallExchange` `0x180036ae0`：DLC 背景墙与格的交换。
- `SimUpdateTemperatureTask::InternalDoTask` `0x1800458d0` 的调用表里是「背景墙交换 ×1 + `UpdateTemperature` ×2 + `DoStateTransition` ×1」，末尾的 `DoStateTransition` `0x1800359e0` 负责相变；「每个格按两个方向配对（水平/垂直）」属**推断**，未逐行读循环结构。
- `DoPartialHeatTransition` `0x18004b7f0`：质量/相态变化时的热量分配。

## 3. 建筑 ↔ 所在格（原生）

`ExchangeHeatEnergyWithWorld` `0x18003f190` + `CalculateTemperatureExchange` 包装：

```
Q = min( ΔT × E × dt , 1.0 × ΔT × C_cell , 1.0 × ΔT × C_building )
E = min( (ins_cell/255)² × k(格元素) , k_building ) × α × 0.001
* α = 调用方倍率 × 建筑数据字段(+0x10)，dt = 调用方传入（C# 侧即 0.2 s）
* 热容限幅系数是 1.0（不是格子间的 0.25），再受 T_eq 钳制
```

前置检查（不满足则本次不交换）：格质量 > 0；格温 ∈ (0, 10000]；建筑温 ∈ [0, 10000]；格元素无 `0x10` 标志位（真空/特殊）。

建筑侧数据由 C# 送入：`StructureTemperatureComponents.UpdateSimState`（行 386579）→ `SimMessages.ModifyBuildingHeatExchange(simHandle, extents, mass, internalTemperature, def.ThermalConductivity, overheatTemperature, operatingKilowatts, elementIdx)`（`SimMessages` 行 421639；结构体行 420970）。

- `mass` = `def.MassForTemperatureModification`；`payload.enabled == false || bypass` 时送 **0**（等于退出换热）。
- 元素 idx = 建筑 `PrimaryElement.Element.idx`，即**主建造材料**。
- 建筑热容 `C_building` = 建筑数据 `+8` 字段；由 `mass` 与主建造材料 SHC 得到属**推断**（未逐条反汇编 `BuildingHeatExchange::Modify` 核实），但 `Modify`/`Register` 是唯一写入该字段的路径。

**关键结论（对 Mod 重要）**：建筑↔格换热里的「建筑侧导热系数」只有 `def.ThermalConductivity`（建造定义里的固定值），**主建造材料的导热系数没有直接进入这条通道**；材料通过 SHC 影响建筑热容，通过质量影响 `mass`。要让材料 k 参与建筑换热，必须自己接入（改 `def.ThermalConductivity` 或另发消息）。

建筑自身温度由原生保存在 `buildingTemperatures`（`StructureTemperatureComponents.OnGetTemperature` 行 386601 直接读它），`SimMessages.ModifyBuildingEnergy`（行 421675）用于按 kJ 直接加减热量，带 `[minTemperature, maxTemperature]` 钳制；`StructureTemperatureComponents.ProduceEnergy`（行 386637）是它的 C# 包装，会记入信息卡的产热明细。

## 4. 建筑 ↔ 建筑（原生）

`StructureToStructureTemperature`（C#，行 386848）在建筑生成/销毁时把「接触到的建筑 + 接触格数」注册给原生：`SimMessages.RegisterBuildingToBuildingHeatExchange` / `AddBuildingToBuildingHeatExchange` / `Remove...`（行 421686-421717，`cellsInContact` 为接触格数，接触格 = 建筑占格去掉输入/输出口格）。

原生 `BuildingToBuildingHeatExchange::Update` `0x18003d160` 逐对计算，写回用 `BuildingHeatExchange::ChangeBuildingTemperature` `0x18003b0f0`（按 handle 直接改原生建筑温度数组）。

## 5. 管道内容物 ↔ 管道（原生 + C# 参数）

参数由 C# `ConduitTemperatureManager.Allocate`（行 242484）给出：

```
conduit_heat_capacity        = def.MassForTemperatureModification × SHC(管道建造材料元素)
conduit_thermal_conductivity = k(建造材料元素) × def.ThermalConductivity
conduit_insulated            = def.ThermalConductivity < 1
```

原生 `ConduitTemperatureManager::Update` `0x18003820`（反汇编可见常量 `0.5` / `50` / `0.001` / `1e-06` / `3` / `min−max` 钳制）：

```
k_pair = 保温管 ? min(k_内容, k_管) : (k_内容 + k_管) × 0.5      // 「平均值」与「保温管取小」
能量   ∝ ΔT × k_pair × 50 × 0.001
两侧温度同样按 [min(T1,T2), max(T1,T2)] 与各自热容钳制
```

冻结/融化由原生回报 handle 列表，C# 侧执行 `FreezeConduitContents` / `MeltConduitContents`（行 242548-242559）。

注意与建筑不同：**管道换热确实乘了建造材料的 k**（还有 def.ThermalConductivity）。

## 6. C# 侧的直接注热/吸热接口（绕过传导）

| 接口 | 行为 | 位置 |
| --- | --- | --- |
| `SimMessages.ModifyEnergy(cell, kilojoules, maxTemperature, id)` | 直接给某格加减 kJ，带最高温钳制，`EnergySourceID` 记录来源 | 行 422129；枚举 421282 |
| `SimMessages.ModifyBuildingEnergy(handle, kJ, minT, maxT)` | 直接给建筑加减 kJ | 行 421675 |
| `StructureTemperatureComponents.ExhaustHeat(extents, kw, maxTemp, dt)` | 排气热：`kw×dt/(宽×高)` 均摊到占地格，每格再乘 `min(mass,1.5)/1.5`，逐格 `ModifyEnergy` | 行 386561 |
| `StructureTemperatureComponents.Sim200ms` | 建筑活动时把 `SelfHeatKilowattsWhenActive`（= `OperatingKilowatts`）交给原生，`ExhaustKilowattsWhenActive` 走上面的排气路径 | 行 386487-386545 |
| `GameUtil.DeltaThermalEnergy` / `CalculateTemperatureChange` | `ΔT = kW/(SHC×mass)`，并夹到目标温度 | 行 281487、281492 |
| `GameUtil.GetFinalTemperature` | 两团物质按质量加权混合并夹在两者温度之间 | 行 281578 |
| `SimUtil.EnergyFlowToTemperatureDelta` | `kJ/(SHC×mass)` | 行 697630 |
| `SimUtil.ClampEnergyTransfer` | 按 `max_watts × dt/1000` 限幅，并保证不过平衡点 | 行 697589 |

生物/其它物体的「与格交换潜力」用 C# 公式（**不是**原生那支）：

```
SimUtil.CalculateEnergyFlow(cell, destTemp, destSHC, destK, area=1, thickness=1)
  = (T_cell − destTemp) × min(k_cell, destK) × (area/thickness) × 0.001      // 行 697568、697573
CreatureTemperature 传入 SurfaceArea / Thickness（属性 ThermalConductivityBarrier）
```

火箭燃料与冷却剂混合用 `GameUtil.ForceConduction(a, b, dt)`（行 281592，调用点行 216116 `dt*5`）：

```
Q = (T_b − T_a) × min(k_a, k_b) × min(m_a, m_b) × dt
Q 再被 |T_eq − T_a|·C_a / |T_eq − T_b|·C_b 的较小值限幅，然后 T = (E + Q) / (SHC × mass)
```

## 7. 相变与过热

- 相变在原生：`DoStateTransition` `0x1800359e0`、`DoLoadTimeStateTransition` `0x18035850`（读档），C# 侧由 `Game.Sim200ms` 接收 `buildingOverheatInfos` / `buildingNoLongerOverheatedInfos` / `buildingMeltedInfos` 并分别触发（行 275678-275688）。
- 建筑过热阈值随 `ModifyBuildingHeatExchange` 送进原生（`overheatTemperature`），原生用 `Payload.maxTemperature` 触发过热事件；这也解释了为什么信息卡改阈值与实际过热判定是同一份数据。

## 8. 对 Mod 接入的含义（待设计判断，不是已定方案）

1. 想改「材料影响建筑换热」，可选入口只有三处：`def.ThermalConductivity`（固定值）、送进原生的 `mass`（`def.MassForTemperatureModification`）、主建造材料元素索引（决定 SHC→建筑热容）。
2. 想让**材料 k** 进入建筑↔格传导，需要改 `def.ThermalConductivity` 或自建注热通道（原生没有读建筑材料的 k）。
3. 想让**材料 SHC** 影响建筑，只需保证 `MassForTemperatureModification` 的建筑热容按主材料算（现行原生已按元素 SHC 算，方法待逐条核实）。
4. 接触面积倍率是元素表数据（气体 25、液体 25、雪 1000），若 Mod 要按材料改变「接触面」，这是唯一现成的数据字段（同时影响所有用该元素的格，无法只改建筑）。
5. `insulation` 字节是「整格」概念，瓦片一次性写入；改它会同时影响该格参与的所有传导。
6. 建筑↔格、建筑↔建筑、管道三条通道参数不同（限幅系数 0.25/1.0、是否乘材料 k、是否乘面积倍率），不能互相外推。

## 9. 尚未核实/存疑

- 建筑数据 `+8`（热容）与 `+0x10` 字段的具体构造过程（推断为 `mass × SHC(主材料)` 与某种倍率），未逐条反汇编核实。
- `BuildingToBuildingHeatExchange::Update` 的具体系数未解码（只核实了「按接触格数成对计算 + 写回接口」）。
- 管道公式里 `50` 与 `ConduitTemperatureManager::Update` 前半段（`xmm6`/`xmm7` 的来源）未完整解码，只核实了「平均/保温取小 + 0.5/50/0.001 + 热容与平衡点钳制」。
- 接触面积倍率字段的**字面语义**（「本元素接触对方相态」）由 `GetSurfaceAreaMultiplier(this, other)` 的取值路径确定，未从 Klei 文档或代码注释二次确认。
- 以上全部为静态核实，**未在游戏内跑对照实验**。
