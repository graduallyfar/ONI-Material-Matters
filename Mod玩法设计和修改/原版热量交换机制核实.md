本文件记录从**本机安装的游戏**（Steam `E:\SteamLibrary\steamapps\common\OxygenNotIncluded`，Steam buildid `24423041`，`SimDLL` 里的 Klei 构建号 `707956`）核实到的原版热量交换算法，供 Mod 设计判断材料属性该从哪里接入。只记录原版事实，不代替玩法设计。

## 1. 单位与时间步

- 温度：°C；质量：kg（`PrimaryElement.Mass`）；比热容 SHC 单位 DTU/(g·°C)。
- 热容 `C = mass(kg) × SHC`，单位 kJ/°C（`GameUtil.GetEnergyInPrimaryElement` = `0.001f * (T × mass*1000 × SHC)`，行 281555）。
- 注热接口用 kJ；建筑产热用 kW（`SelfHeatKilowattsWhenActive` / `ExhaustKilowattsWhenActive`）。
- 单元格温度更新在原生 `UpdateTemperature` 内写死 **0.2 s** 步长（`0x180036976` 处加载 double 常量 0.2）；C# 侧 `Sim200ms` 同为 5 Hz。

### 1.1 状态是温度，运算是热量

原版**不是**给每个对象存一份「热量」再搬运，而是：

1. **持久状态只有温度**。传导用到的单元格状态只有元素 idx、温度、质量、insulation 四个数组（`UpdateTemperature` 里按 `[cellSOA+0x08]` 元素、`+0x28` 温度、`+0x48` 质量、`+0x88` insulation 取值），没有能量字段；热容每次现算 `mass × SHC(元素)`。
2. **一次交换的中间量是热量**：先按 `Q = ΔT × K × A × dt`（再加热容限幅）算出这次搬运了多少 kJ。
3. **结算成温度**：同一次交换里，冷侧 `+Q/C_cold`、热侧 `−Q/C_hot`——**同一份热量，两边温升不同**，重/高比热容的一侧几乎不动；再用 `T_eq` 双向钳制，不允许越过平衡点。
4. **写回的是温度**：`新温度 − 当前温度` 累加进本帧的工作温度数组（与当前温度数组分开的两份缓冲），最后把工作值 clamp 到 `[1, 10000]`。
5. 因此能量守恒不是靠“能量账本”，而是靠「同一个 Q 一进一出、两侧各除自己的热容」保证；热量在配对内部存在，配对结束后只剩温度。

例外与补充（同样是「温度存状态、热量做接口」）：

- 掉落物/碎片 `Sim.ElementChunkInfo`（行 420415）字段是 `{temperature, deltaKJ}`：状态是温度，`deltaKJ` 只是上一帧交换的热量回报（`ElementChunk` 用它算平均功率，行 245429）；`SimMessages.ModifyElementChunkEnergy(handle, kJ)`（行 421583）是按热量改它的入口。
- 建筑状态是温度（`buildingTemperatures`，`BuildingTemperatureInfo {handle, temperature}` 行 420447），但改它的接口是热量：`ModifyBuildingEnergy(handle, kJ, min, max)`（行 421675）／`ProduceEnergy`（行 386637）；`SelfHeatKilowattsWhenActive` 这类 kW 值乘 dt 换成 kJ。建筑的原生记录布局见 §3 表格（温度 / 过热阈值 / 运行 kW / 总热容 / 每格热容 / 导热系数 / 占地范围）。C# 里另有 `Sim.BuildingConductivityData {temperature, heatCapacity, thermalConductivity}`（行 420455）镜像结构，本版本 C# 内无调用点。
- 质量合并/相变按能量加权混合：`T_eq = (T_a C_a + T_b C_b)/(C_a + C_b)`，C# 镜像见 `GameUtil.GetFinalTemperature`（行 281578）、`SimUtil.CalculateFinalTemperature`（行 697639）。

对 Mod 的含义：要给某个东西升温，应当走**热量**接口（kJ / kW × dt，或 `ModifyBuildingEnergy`、`ModifyEnergy`、`ProduceEnergy`），不要直接写温度；直接写 `PrimaryElement.Temperature` 只改状态，会立刻影响后续传导，但不带「这份热量从哪来」的守恒语义。反过来，因为每格热容 = 质量 × SHC，同一份热量对不同材料的温升天然不同——这就是材料进入热量系统的入口。

## 2. 单元格 ↔ 单元格（原生，主要传导通道）

符号与地址：`UpdateTemperature` `0x180036470`（1636 B），`details::CalculateTemperatureExchange_precise` `0x180035670`，`CalculateTemperatureExchange`（float 包装）`0x180035590`，`ElementTemperatureData::GetSurfaceAreaMultiplier` `0x1800361f0`，`CellSOA::GetInsulationValue` `0x1800361b0`。

对相邻两格 a、b：

```
C_i   = mass_i × SHC(元素_i)
ΔT    = T_hot − T_cold
K     = 两格 insulation 均为 255(1.0) 时  sqrt(k_a × k_b)
        否则                             min( k_a × (ins_a/255)² , k_b × (ins_b/255)² )
A     = SurfaceAreaMultiplier(元素_a, 相态_b) × SurfaceAreaMultiplier(元素_b, 相态_a)
E     = K × A
Q     = min( ΔT × E × 0.2 , 0.25 × ΔT × C_cold , 0.25 × ΔT × C_hot )     // 0.2 = 时间步(s)
T_eq  = (T_a·C_a + T_b·C_b) / (C_a + C_b)
T_cold' = min(T_cold + Q / C_cold, T_eq)
T_hot'  = max(T_hot  − Q / C_hot , T_eq)
最终两格温度统一 clamp 到 [1, 10000]
```

要点：

- 几何平均那支不是直接开方，而是 `exp(0.5 × (log a + log b))`（调用 `logf`/`expf`，`0x1800a3230` / `0x1800a2f80`），数学等价于 √(k_a·k_b)。
- **两个 0.25 是热容限幅**（每步最多移动「把该格推到对侧温度所需能量」的 1/4），配合 `T_eq` 钳制，避免振荡。格子越重（C 越大）越不容易被瞬时拉平。
- 相态由 `元素state & 3` 决定：`1`→固、`2`→液、`3`→气，取的是**对方相态**对应的本元素倍率（`GetSurfaceAreaMultiplier(this, other)`）。
- `insulation` 是每格的字节，默认 255（`Sim.Cell.SetValues`，行 419689）；`SimMessages.SetInsulation(cell, value)`（行 421915）由瓦片写入，瓦片写 `def.ThermalConductivity`、非瓦片写 1.0（行 294731、294736）。所以**只要有任何一格被瓦片改过 insulation，就落进 min 支**：保温砖 `0.01` → `(0.01)² = 1e-4` 量级的系数。
- 气压/质量不影响 K，只通过 C 影响限幅。
- 空气-固体接触面积倍率很大，见下节数据。

### 2.1 接触面积倍率（元素数据，实测摘录）

数据文件 `StreamingAssets\elements\{solid,liquid,gas}.yaml`，字段 `solidSurfaceAreaMultiplier` / `liquidSurfaceAreaMultiplier` / `gasSurfaceAreaMultiplier` 表示「本元素接触对方某相态时的面积倍率」。

- 全部气体：`solid=25, liquid=1, gas=1`
- 全部液体：`solid=1, liquid=25, gas=1`
- 绝大多数固体：`1,1,1`；例外：`Snow/CrushedIce/StableSnow` 为 `1,1,1000`，`TempConductorSolid` 全为 `2`，`Unobtanium`、`Vacuum`、`Void`、`COMPOSITION` 全为 `0`
- 值分布（212 个元素，共 636 个字段）：`1`×534、`25`×84、`0`×12、`1000`×3、`2`×3

由此：气↔固 = 25×1 = 25；液↔液 = 25×25 = 625；固↔固 = 1；雪↔气 = 1000×25 = 25000（雪因此快速吸热融化）。

### 2.2 同族公式

- `UpdateTemperatureForBackwallExchange` `0x180036ae0`：DLC 背景墙与格的交换。
- `SimUpdateTemperatureTask::InternalDoTask` `0x1800458d0` 的调用表里是「背景墙交换 ×1 + `UpdateTemperature` ×2 + `DoStateTransition` ×1」，末尾的 `DoStateTransition` `0x1800359e0` 负责相变；「每个格按两个方向配对（水平/垂直）」属**推断**，未逐行读循环结构。
- `DoPartialHeatTransition` `0x18004b7f0`：质量/相态变化时的热量分配。

## 3. 建筑 ↔ 所在格（原生）

**入口是 `BuildingHeatExchange::Update` `0x18003ba90`（BuildingHeatExchange.obj），不是 `ExchangeHeatEnergyWithWorld`**（后者属 `ElementChunk.obj`，见 §3bis）。`Update` 按建筑记录的 `minX/minY/maxX/maxY` 双重循环遍历占地格，逐格与该建筑交换。

```
C_cell  = 格质量 × SHC(格元素)
k_cell  = 格元素导热系数
k_bldg  = k(主建造材料元素) × def.ThermalConductivity      // InitializeFromMessageData 0x18003b530
C_bldg  = (MassForTemperatureModification × SHC(主建造材料)) / 建筑格数   // 按占地格数平摊
ΔT      = T_cell − T_bldg
Q       = ΔT × C_donor × k_cell × k_bldg × (ins_cell/255)² × 0.005 × dt × [网格对象+0xb0]
          C_donor = ΔT ≥ 0 ? C_cell : C_bldg              // 取“正在放热那一侧”的热容
T_cell' = clamp(T_cell − Q / C_cell , min(T_cell,T_bldg) , max(T_cell,T_bldg))
T_bldg' = clamp(T_bldg + Q / C_bldg , min(T_cell,T_bldg) , max(T_cell,T_bldg))
若符号检查失败（会越过平衡点）→ 两侧直接取 T_eq = (C_cell·T_cell + C_bldg·T_bldg)/(C_cell+C_bldg) 再夹紧
```

- `0.005 × dt` 在 dt = 0.2 s 时正好等于 `0.001`，与其它通道的单位换算系数一致；常量 `7.68935e-08` 等于 `0.005 / 255²`，把 `ins²` 折算成 `(ins/255)²`。
- `[网格对象+0xb0]` 是调用侧传入的浮点倍率，语义**未核实**（若为 1.0 则上式即为完整系数）。
- 格温度**直接写回 CellSOA 温度数组**（`0x18003bf42`：`movss [rcx+rdi*4],xmm6`，rcx = `[CellSOA+0x28]`），建筑温度写回记录 `+0`（`0x18003c133`），之后逐格调用 `DoStateTransition`（相变/过热检查）。

前置检查（不满足则该格不交换）：格质量 ≤ 0；建筑温度 < 0；建筑记录热容 ≤ 0（C# 送 `mass = 0`，即停机/旁路时就是这种情况）；建筑占地与当前活动区域无交集。

建筑记录布局（`InitializeFromMessageData` `0x18003b530` 写入、`Update` 读取，步长 0x2c）：

| 偏移 | 语义 | 来源 |
| --- | --- | --- |
| `+0x00` | 建筑温度 | 消息 `temperature`（要求 ∈ [0, 10000]） |
| `+0x04` | 过热阈值 | 消息 `overheatTemperature` |
| `+0x08` | 运行产热 kW | 消息 `operatingKilowatts` |
| `+0x0c` | 总热容 = mass × SHC(主材料) | 由 `mass` 与元素 SHC 现算 |
| `+0x10` | **每格热容** = 总热容 ÷ 格数 | 同上（换热实际用这一项） |
| `+0x14` | 建筑导热系数 = k(主材料) × def.ThermalConductivity | 元素 k 与定义值相乘 |
| `+0x18` | 元素数据 `+0x2c` 字段 | 未核实（疑似某种倍率） |
| `+0x1c..0x28` | minX/minY/maxX/maxY（各 +1） | 消息 extents |

建筑侧数据由 C# 送入：`StructureTemperatureComponents.UpdateSimState`（行 386579）→ `SimMessages.ModifyBuildingHeatExchange(simHandle, extents, mass, internalTemperature, def.ThermalConductivity, overheatTemperature, operatingKilowatts, elementIdx)`（`SimMessages` 行 421639；结构体行 420970）。

- `mass` = `def.MassForTemperatureModification`；`payload.enabled == false || bypass` 时送 **0**（等于退出换热）。
- 元素 idx = 建筑 `PrimaryElement.Element.idx`，即**主建造材料**。

**关键结论（对 Mod 重要）**：材料进入建筑↔格换热的路径是「主建造材料 SHC → 总热容 → 每格热容」与「k(主建造材料) × `def.ThermalConductivity` → 建筑导热系数」。**材料 k 是作为乘积的一半参与的**——此前「材料 k 不参与建筑换热」的说法是错的，正确说法是它始终被 `def.ThermalConductivity` 这个固定值缩放。另外换热按占地格数平摊建筑热容：N 格建筑的每一格只面对 1/N 的建筑热容。

建筑温度同时保留在 `buildingTemperatures` 数组供 C# 读取（`StructureTemperatureComponents.OnGetTemperature` 行 386601；`BuildingHeatExchange::ChangeBuildingTemperature` `0x18003b0f0` 按 handle 写该数组）；`SimMessages.ModifyBuildingEnergy`（行 421675）用于按 kJ 直接加减热量，带 `[minTemperature, maxTemperature]` 钳制；`StructureTemperatureComponents.ProduceEnergy`（行 386637）是它的 C# 包装，会记入信息卡的产热明细。

## 3bis. 物件/生物 ↔ 所在格（原生，`ElementChunk`）

C# 入口是 `SimTemperatureTransfer`（行 362893）：`SimRegister` 调 `SimMessages.AddElementChunk(gameCell, element, mass, temperature, surface_area, thickness, ground_transfer_scale, cb)`（行 421526，调用点行 363148）。复制人、小动物（`CreatureSimTemperatureTransfer`）、掉落矿石与食物都走这条。

原生实现：`ElementChunk::Update` `0x18003f860` → 逐格调用 `ExchangeHeatEnergyWithWorld` `0x18003f190`，内部用 `CalculateTemperatureExchange`（float 包装 `0x180035590`）：

```
Q = min( ΔT × E × dt , 1.0·ΔT·C_cell , 1.0·ΔT·C_obj )
E = min( (ins_cell/255)² × k(格元素) , k_obj ) × α × 0.001
    α = 调用方倍率 × 记录字段(+0x10)   // 很可能是 surface_area 或 surface_area/thickness，未核实
记录字段：+0x04 温度、+0x08 热容、+0x0c 导热系数
```

前置检查（`0x18003f190`-`0x18003f408`）：格质量 ≤ 0；物温 < 0 或 > 10000；格温 > 10000；格元素带 `0x10` 标志位（真空/特殊）→ 本次不交换。

C# 侧另有两条与生物相关的公式（用于「潜力/显示」，不是上面这条原生通道的替代）：`SimUtil.CalculateEnergyFlow(cell, temp, shc, k, area, thickness) = ΔT × min(k) × (area/thickness) × 0.001`（行 697568）；`CreatureSimTemperatureTransfer.PotentialEnergyFlowToCreature`（行 245472，取 `SurfaceArea` / `Thickness` 属性）。

按热量直接改物件用 `SimMessages.ModifyElementChunkEnergy(handle, kJ)`（行 421583），原生 `ElementChunk::ModifyEnergy` `0x18003f570`；物件把换热结果回报在 `Sim.ElementChunkInfo.deltaKJ`（行 420415）。

## 4. 建筑 ↔ 建筑（原生）

`StructureToStructureTemperature`（C#，行 386848）在建筑生成/销毁时把「接触到的建筑 + 接触格数」注册给原生：`SimMessages.RegisterBuildingToBuildingHeatExchange` / `AddBuildingToBuildingHeatExchange` / `Remove...`（行 421686-421717，`cellsInContact` 为接触格数，接触格 = 建筑占格去掉输入/输出口格）。

## 5. 管道内容物 ↔ 管道（原生 + C# 参数）

参数由 C# `ConduitTemperatureManager.Allocate`（行 242484）给出：

```
conduit_heat_capacity        = def.MassForTemperatureModification × SHC(管道建造材料元素)
conduit_thermal_conductivity = k(建造材料元素) × def.ThermalConductivity
conduit_insulated            = def.ThermalConductivity < 1
```

原生 `ConduitTemperatureManager::Update` `0x18003820`（反汇编可见常量 `0.5` / `50` / `0.001` / `1e-06` / `3` / `min−max` 钳制）：

```
k_pair = 保温管 ? min(k_内容, k_管) : (k_内容 + k_管) × 0.5      // 「平均值」与「保温管取小」
能量   ∝ ΔT × k_pair × 50 × 0.001
两侧温度同样按 [min(T1,T2), max(T1,T2)] 与各自热容钳制
```

冻结/融化由原生回报 handle 列表，C# 侧执行 `FreezeConduitContents` / `MeltConduitContents`（行 242548-242559）。

注意与建筑不同：**管道换热确实乘了建造材料的 k**（还有 def.ThermalConductivity）。

生物/其它物体的「与格交换潜力」用 C# 公式（**不是**原生那支）：

```
SimUtil.CalculateEnergyFlow(cell, destTemp, destSHC, destK, area=1, thickness=1)
  = (T_cell − destTemp) × min(k_cell, destK) × (area/thickness) × 0.001      // 行 697568、697573
CreatureTemperature 传入 SurfaceArea / Thickness（属性 ThermalConductivityBarrier）
```

火箭燃料与冷却剂混合用 `GameUtil.ForceConduction(a, b, dt)`（行 281592，调用点行 216116 `dt*5`）：

```
Q = (T_b − T_a) × min(k_a, k_b) × min(m_a, m_b) × dt
Q 再被 |T_eq − T_a|·C_a / |T_eq − T_b|·C_b 的较小值限幅，然后 T = (E + Q) / (SHC × mass)
```

## 7. 相变与过热

- 相变在原生：`DoStateTransition` `0x1800359e0`、`DoLoadTimeStateTransition` `0x18035850`（读档），C# 侧由 `Game.Sim200ms` 接收 `buildingOverheatInfos` / `buildingNoLongerOverheatedInfos` / `buildingMeltedInfos` 并分别触发（行 275678-275688）。
- 建筑过热阈值随 `ModifyBuildingHeatExchange` 送进原生（`overheatTemperature`），原生用 `Payload.maxTemperature` 触发过热事件；这也解释了为什么信息卡改阈值与实际过热判定是同一份数据。

## 8. 对 Mod 接入的含义（待设计判断，不是已定方案）

1. 想改「材料影响建筑换热」，可用入口是：`def.ThermalConductivity`（固定值，与主材料 k 相乘）、`def.MassForTemperatureModification`（决定总热容，再按占地格数平摊）、主建造材料元素（同时提供 k 与 SHC）。
2. 材料 k 已经通过「k(主材料) × def.ThermalConductivity」进入建筑↔格传导；若要让材料 k 单独决定（而不被定义值缩放），需要改 `def.ThermalConductivity` 或自建注热通道。
3. 材料 SHC 通过 `mass × SHC` 影响建筑热容；建筑格数越多，每格面对的 `C_bldg` 越小（同样一份热量引起更大温升）。
4. 接触面积倍率是元素表数据（气体 25、液体 25、雪 1000），**只在格↔格传导里使用**；建筑↔格与物件↔格都不乘它。
5. `insulation` 字节是「整格」概念，瓦片一次性写入；改它会同时影响该格参与的所有传导。
6. 各通道参数不同（格↔格 0.2 步长 + 0.25 热容限幅 + 面积倍率；建筑↔格 按格平摊热容 + k 相乘 + 0.005·dt；物件↔格 min(k) + 面积/厚度 + 0.001），不能互相外推。

## 9. 尚未核实/存疑

- 建筑↔格的公式已逐条反汇编核实（`BuildingHeatExchange::Update` 0x18003ba90 + `InitializeFromMessageData` 0x18003b530）；仍存疑的是：`[网格对象+0xb0]` 倍率语义、建筑记录 `+0x18`（元素数据 `+0x2c`）字段用途、以及记录 extents 为何统一 +1（未影响「按占地格交换」的结论，但逐格坐标是否偏移一格未验证）。
- 物件↔格（`ElementChunk`）的记录字段 `+0x10`（面积/厚度类倍率）语义未核实。
- `BuildingToBuildingHeatExchange::Update` 的具体系数未解码（只核实了「按接触格数成对计算 + 写回接口」）。
- 管道公式里 `50` 与 `ConduitTemperatureManager::Update` 前半段（`xmm6`/`xmm7` 的来源）未完整解码，只核实了「平均/保温取小 + 0.5/50/0.001 + 热容与平衡点钳制」。
- 接触面积倍率字段的**字面语义**（「本元素接触对方相态」）由 `GetSurfaceAreaMultiplier(this, other)` 的取值路径确定，未从 Klei 文档或代码注释二次确认。
- `UpdateTemperature` 写回的那份温度缓冲是「本帧工作温度副本」还是「上一帧/事件用温度」，由「累加 `新温度 − 当前温度` 后夹到 `[1,10000]`」推断，未追到该缓冲的初始化与最终提交点。
- 以上全部为静态核实，**未在游戏内跑对照实验**。
