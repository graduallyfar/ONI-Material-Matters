# v0.0.2 开发文档

本篇记录 v0.0.2 的实现方式与待定项，只覆盖两件事：**订单流程完善**与**金属精炼器实装**（配方温区数值 + 过热阈值规则）。

机制含义以 [[2. 建筑系统设计细节]] 为准，本篇只说明怎么实现。**本篇不代替设计文档。**

# 2. 订单流程

## 2.1 为什么需要订单表

原版 `ComplexFabricator` 的后端是**每配方一个计数**的字典（`recipeQueueCounts`）加一个 `recipe_list` 下标指针（`nextOrderIdx`），因此：

- 无法表达「炼铜 → 炼铁 → 再次炼铜」这种同一配方出现在不同位置的要求；
- 轮换按 `recipe_list` 顺序（配方标识排序）而不是玩家添加顺序；
- 有限订单不会连续执行完，而是与其他可执行配方轮转。

设计（细节文档 §2.3）要求按玩家添加顺序、允许重复、有限订单连续执行、无限订单按轮次让出，所以必须有第二份**有序订单表**。

## 2.2 两份数据的关系

| 数据 | 归属 | 作用 |
| --- | --- | --- |
| `OrderQueue`（`Orders/`，判断层） | 本 Mod | 订单顺序、每笔订单的剩余批次数、无限订单本轮进度、轮换指针、已锁定批次 |
| `recipeQueueCounts`（原版私有字典） | 原版，本 Mod 改写 | 侧屏数量显示、预取数量、原版可用性判断 |
| `nextOrderIdx` / `nextOrderIsWorkable`（原版私有字段） | 原版，本 Mod 改写 | 原版「下一个开始哪个订单」的判断结果 |

**折算口径：** 某配方的原版计数 = 该配方所有有限订单的剩余批次之和；只要存在一笔无限订单，就写原版的无限哨兵 `-1`（`ComplexFabricator.QUEUE_INFINITE`）。折算集中在 `MaterialOverhaulFab.SyncVanillaCount`，只写本次变化涉及的配方，不整表重写。

**旧存档哨兵：** 原版 `ComplexFabricator.OnSpawn` 会把数量 100 改写成无限，因此导入时把 `-1` 与 `100` 都识别为无限订单（`FabricatorAccess.LegacyInfiniteCount`），避免把旧存档的无限订单读成 100 批。

`SideTable` 式的只读迁移：`EnsureOrdersImported` 把「原版计数里有数量、订单表里没有」的配方按原版配方顺序补进订单表，因此旧存档、控制台、其它 Mod 直接改原版计数都不会让订单永远轮不到。导入会逐条记录日志。

## 2.3 轮换接管

| 补丁 | 类型 | 作用 |
| --- | --- | --- |
| `ComplexFabricator.AdvanceNextOrder` | 前缀，跳过原方法 | 有本 Mod 订单数据时改由订单表扫描；无数据时保持原版 |
| `ComplexFabricator.RefreshAndStartNextOrder` | 前缀 | 每次刷新前先重算「下一笔」，因此批次完成后立刻按新状态选择 |
| `ComplexFabricator.StartWorkingOrder` | 前缀 | 锁定开始生产的那一笔订单（重复配方靠轮换位置区分） |
| `ComplexFabricator.CompleteWorkingOrder` | 前缀 + 后置 | 前缀记账，后置同步原版计数 |

选择逻辑（`MaterialOverhaulFab.RefreshNextOrder`）：

1. 从订单表的轮换位置按添加顺序检查，取第一笔**可执行**的订单；
2. 可执行 = 配方在本建筑配方列表中、原版 `GetRemainingQueueCount > 0`、原版 `HasIngredients` 为真；
3. 全部不可执行时把 `nextOrderIsWorkable` 置假并**不移动轮换指针**，等材料或订单变化后再检查（不空转）；
4. 找到候选后把原版 `nextOrderIdx` 指向该配方在 `recipe_list` 中的下标。

`HasIngredients` 是受保护**虚**方法（`LiquidCooledRefinery` 覆写以要求冷却液充足），所以接入层用反射调用保证虚分派，不绑成基类委托；`GetRemainingQueueCount` 是私有非虚方法，用 Harmony 的开放委托直接调用。两者都不复制原版逻辑。

> **材料齐备口径：** 设计要求「输入存储与加工存储合并计算」。实现上仍用原版 `HasIngredients(inStorage)`：正在生产的那一批，原料已经由原版转入加工存储、并且批次被原版锁定（`ValidateWorkingOrder` 只看队列是否还有该配方，不看输入仓），所以「已投料视为本批次材料齐全」已经成立。若再把加工存储计入可用量，同一批原料会被算两次（原版 `GetRemainingQueueCount` 已经把在产批次从计数里扣掉），因此这里**刻意不合并**。

## 2.4 界面入口映射

三个入口都在 `ComplexFabricatorSideScreen`（已核实）：

| 原版入口 | 原版行为 | 本 Mod 动作 |
| --- | --- | --- |
| `IncrementRecipeQueueCount`（「+」） | 计数 +1；已是无限时清零；到达 99 上限后变无限 | 追加一笔 1 批订单；无限→清零则移除该配方订单；到达上限→整笔替换为无限订单 |
| `DecrementRecipeQueueCount`（「−」） | 计数 −1；`respectInfinite:false` 时无限→99，0→无限 | 回退**最后一笔**同配方订单；无限→按 99 批记账；0→无限这种原版怪行为**不凭空创建订单**，把计数改回 0 并记日志 |
| `SetRecipeQueueCount`（「∞」与数量输入） | 直接写计数 | 0 取消该配方全部订单；−1 记为一笔无限订单；正数改写为一笔对应批次的订单，**位置沿用原来第一笔的位置** |

前缀负责在改原版计数**之前**对齐订单表（`EnsureOrdersImported`），后置执行上述动作并写回计数，避免「原版已经加过、订单表再补一次」的重复计数。

每笔无限订单有「本轮批次数」。玩家额度输入属后续版本，当前用 `OrderEntry.PlaceholderInfiniteBatchQuota = 1` 占位：无限订单每完成一批就让出给后面的订单，不会独占建筑（**占位值，不是最终数值**）。

## 2.5 批次完成的记账顺序

`CompleteWorkingOrder` 的正文是：结算产物 → 扣减原版计数 → 调用 `RefreshAndStartNextOrder` 开始下一批。因此：

- **记账放在前缀**：无限订单的本轮额度必须在这一步之前生效，否则 `RefreshAndStartNextOrder` 会在额度用完后又把同一笔无限订单启动一次（额度为 1 时表现为连做两批）；
- **计数同步放在后置**：原版正文内部走的是私有的 `DecrementRecipeQueueCountInternal`，不经过公开 API，后置以订单表为准写回。

取消当前订单沿用原版路径：侧屏把数量设为 0 → 原版 `RefreshQueue` → `ValidateWorkingOrder` 发现该配方已不在队列 → `CancelWorkingOrder` 把加工存储里的原料退回输入存储、进度清零。本 Mod 只负责把订单从订单表移除（`LockedIndex` 同时失效），**不另写一套取消流程**。

## 2.6 读档与持久化

| 数据 | 处理 |
| --- | --- |
| 订单顺序、每笔剩余数量、无限额度、本轮进度、轮换位置 | 本 Mod 自有字段，随存档落盘 |
| 原版计数字典 | 读档后按订单表重新折算，不重复投料、不重复结算 |
| 已锁定批次 | 原版 `workingOrderIdx` 本来就不存档，本 Mod 同样在 `Restore` 时清空，读档后按实际材料与温度重新选择 |
| 原版计数里有、订单表里没有的配方 | `EnsureOrdersImported` 在读档后的 `OnSpawn` 与每次轮换前补齐 |

## 2.7 与原版的差异（有意的）

| 项 | 原版 | 本版 |
| --- | --- | --- |
| 轮换顺序 | 按 `recipe_list`（配方标识排序）轮转 | 按玩家添加顺序 |
| 同配方多笔订单 | 无法表达，只有一个计数 | 保留为多笔独立订单，位置各自保留 |
| 有限订单 | 与其他配方轮转 | 原料持续齐备时连续执行到数量完成 |
| 无限订单 | 一直可执行 | 每轮 1 批（占位额度）后让出 |
| 数量显示 | 每配方一个数 | 仍显示每配方合计（与订单表折算一致） |

## 2.8 待定项

| 项 | 状态 |
| --- | --- |
| 无限订单每轮额度的交互与数值 | 占位 1 批，等侧屏控件 |
| 侧屏的当前生产／下一生产预告 | 不在本版 |
| 预取策略 | 沿用原版 `min(2, 剩余)`，未按订单表调整 |

# 3. 金属精炼器配方温区

## 3.1 登记方式

**不直接写配方标识字符串**，而是写「建筑 + 输入材料 + 输出材料」，由接入层到原版配方表里解析（`ContentRegistration.FindRecipe`）。原因：配方标识由建筑名与材料名拼接而成（`ComplexRecipeManager.MakeRecipeID`），直接写字符串会随标识格式或材料名变化而静默失配。

目录（`Zones/RecipeZoneCatalogue.cs`）只放**用户已经定下的数值**；未登记配方不占位。

## 3.2 已确认数值

| 建筑 | 配方 | 最低可工作 | 最佳温区 | 最高可工作 | 来源 |
| --- | --- | --- | --- | --- | --- |
| MetalRefinery | `AluminumOre` → `Aluminum` | 300 ℃ / 573.15 K | 450–650 ℃ / 723.15–923.15 K | 800 ℃ / 1073.15 K | 用户给定 |

摄氏度到开尔文的换算集中在 `Core/Temperatures.cs`，不在各处写 `+273.15`。

## 3.3 未配置配方的日志

- 目录条目解析失败：`配方温区：未能在原版配方表里找到 …`（按条目只报一次）；
- 名单内建筑仍有未配置配方：`MetalRefinery：配方温区已配置 1/N 条，其余配方暂按原版行为运行（四边界数值待定）。`（按建筑只报一次）；
- 生产时用到未配置配方：沿用 V0.0.1 的 `GetOrLogMissing` 退化日志。

## 3.4 登记时机：必须在配方注册之后（游戏内已踩坑并修正）

**这是本版最关键的实现修正。** 首次部署后的游戏日志显示：

```
[INFO] [MaterialOverhaul] v0.0.2 已加载。白名单建筑 5 项，配方温区条目 0，要求硬度条目 0。
[INFO] [MaterialOverhaul] 过热规则：MetalRefinery 的过热阈值取主建造材料熔点的 0.85。
[WARN] [MaterialOverhaul] 配方温区：未能在原版配方表里找到 MetalRefinery：AluminumOre → Aluminum…
…
[INFO] [MaterialOverhaul] MetalRefinery：MetalRefinery_I_AluminumOre_O_Aluminum 未配置温区，温度 292.6 K，按原版行为运行。
```

原因（已由日志时间线核实）：**`Db.Initialize` 跑在建筑预制件创建之前**。原版配方在建筑配置类的 `ConfigureBuildingTemplate` 里只进 `ComplexRecipeManager.preProcessRecipes`，直到 `Assets.CreatePrefabs` 末尾调用 `ComplexRecipeManager.PostProcess()` 才转入 `recipes`。所以：

- 在 `Db.Initialize` 后置里登记配方温区**一定落空**（当时 `recipes` 是空的），温区整套静默失效：建筑在常温下照样生产、配方界面没有温度文本；
- 同一原因也让调试样例温区一条都没写进去。

修正（三层，任一层命中即可）：

1. **正时机**：新增 `ComplexRecipeManager.PostProcess` 后置补丁 → `ContentRegistration.Apply()` + `DebugValueApplier.Apply()`，此时配方表已就绪；
2. **不误标完成**：配方表为空时 `ContentRegistration` 不置 `ZonesResolved`、`DebugValueApplier` 不置 `applied`，只记一条「将在配方注册完成后重试」的日志，留出重试机会；
3. **兜底重试**：建筑第一次要用配方时（`MaterialOverhaulFab.UpdateCachedZone`）若发现 `ZonesResolved` 仍为假，就再调一次 `Apply()` 并重查侧表。

过热规则不受影响：它只依赖建筑预制件与元素表，在 `Db.Initialize` 后置里登记即可（日志确认玄武岩建造的精炼器阈值已被设为 1300.5 K）。

# 4. 过热阈值

## 4.1 规则与适用范围

$$
T_{overheat} = 0.85 \times T_{melt}(\text{主建造材料})
$$

- 主建造材料与硬度系统同一取值口径：`PrimaryElement.Element`（建造记录第一个材料，缺省时回退本体元素）。
- 熔点取元素自身的熔点字段（固体的熔化温度），来自游戏元素表。
- **只对已经纳入温区数值的建筑生效**：`ContentRegistration.RegisterOverheatRules` 从配方温区目录里取出建筑名单，逐个登记比例 0.85。没有温区数值的建筑不启用，避免在没有温度需求的前提下改动原版过热行为。
- 熔点不可用（缺失、非正、非有限）时不覆盖原版阈值，只记一次日志。

## 4.2 为什么改属性而不是改原版判断

原版过热判定在 SIM 侧：`StructureTemperatureComponents.UpdateSimState` 每次都重新读取 `payload.overheatable.OverheatTemperature` 并推给 SIM。因此只要：

1. 让 `Overheatable` 的属性总值等于规则值；
2. 把该建筑的结构温度标脏（`Disable` + `Enable`，原版 `Overheatable.OnSpawn` 用的就是这个办法）；

原版的过热损伤、过热状态项、通知与维修流程全部继续按原版工作，本 Mod 不需要另写伤害通道，也不需要替换过热状态机。

属性总值的处理方式：先写 `baseOverheatTemp`，读一次 `OverheatTemperature` 触发原版 `InitializeModifiers`，再用本 Mod 的一条修正项把「原版基础值 + 建造材料自带的过热加成」一起补偿掉，使总值恰好等于规则值。这样属性面板显示的阈值与实际判定一致，且重复调用结果稳定（用 `总值 − 本 Mod 修正项` 求固定部分，不会叠加）。

> 没有采用「打补丁改 `OverheatTemperature` 取值」的做法：那样 SIM 与状态项会拿到规则值，但建筑属性面板仍显示原版数值，玩家会看到两个不同的过热温度。

`overheatApplied` 为假时，`TickDamage`（每 200 ms）会补一次应用，覆盖「spawn 时主建造材料还没就绪」的情况。

## 4.4 新增文本的本地化

过热温度属性的修正项说明需要一条新键 `STRINGS.BUILDING.ATTRIBUTES.MATERIALOVERHAUL.OVERHEAT.DESCRIPTION`。

按当前已核实的本地化机制（V0.0.1 开发计划 §3.8）：键必须先在 `Game/ModStrings.cs` 的 LocString 字段树里建出来，再由 `MaterialOverhaulMod.RegisterStrings` 注册；只往 `mod/strings/zh.po` 里加条目**不会**建键，界面会显示 `MISSING.STRINGS.*`。因此本次：

- `Game/ModStrings.cs`：在 `BUILDING` 分支下新增 `ATTRIBUTES.MATERIALOVERHAUL.OVERHEAT.DESCRIPTION`，字段默认值直接给中文；
- `mod/strings/zh.po`：同步加一条同样的 `msgctxt`／`msgstr`，供后续多语言覆盖使用。

## 4.3 与温区的关系

两者的后果不同、阈值独立：温区上限只停止生产与内置加热，过热阈值决定是否受损。要让建筑在某个配方的整个温区内不受损，需要 $T_{melt} \times 0.85 > T_{work,max}$。金属精炼器铝矿配方需要熔点高于 1262.5 K 的材料，可行材料对照表见细节文档 §2.1.5。

# 5. 硬度与维修（沿用 v0.0.1）

本版**不改**硬度与维修逻辑，只跟随过热阈值的来源变化：维修时「只有机械损坏不重置温度、含过热才按原版重置」的判定继续读 `Overheatable.OverheatTemperature`，因此自动使用规则值。机械磨损的伤害转换系数与要求硬度名单仍是待定项（V0.0.1 开发计划 §10 第 9、10 项）。

# 6. 信息卡与配方温度显示

细节文档 §2.3.5 的显示要求里，本版只做「让玩家知道有温度工作区间这件事」，其余（当前生产／下一生产、材料状态、状态栏）仍待实现。两处显示都由**原版已有的字符串出口**追加，不新建界面、不复制原版 UI 逻辑。

## 6.1 建筑信息卡：一句话说明

原版 `BuildingDef.Desc` 是**计算属性**：

```csharp
public string Desc => Strings.Get("STRINGS.BUILDINGS.PREFABS." + PrefabID.ToUpper() + ".DESC");
```

建筑详情页（`DetailsPanel.RefreshInfoPanel` 读 `BuildingComplete.Desc` → `Def.Desc`）与建造菜单（同一属性）都走这里，因此在 `BuildingDef.get_Desc` 上做后置补丁，把一句话追加到原版描述之后：

> 本建筑需要在当前配方的工作温区内运行：低于最低可工作温度时停产预热，高于最高可工作温度时停产等待降温，最佳温区内才是满效率。

- 文本键 `STRINGS.BUILDINGS.PREFABS.MATERIALOVERHAUL.TEMPZONE_NOTE`，默认值即中文（本地化机制见 §4.4）。
- **只对已有配方温区数值的建筑生效**（`ContentRegistration.HasConfirmedZone`），没有数值的建筑保持原版描述，不暗示一个还不存在的约束。
- 追加前先检查文本是否已包含该句，避免重复叠加。

## 6.2 配方选择：显示工作温区范围

原版 `ComplexRecipe.GetUIName(bool)` 提供配方显示名，侧屏的**配方行标签**、**配方详情标题**、行工具提示、「当前订单／下一订单」标签都用它。因此在 `ComplexRecipe.GetUIName` 上做后置补丁，对**有温区数值的配方**把范围接在名字后面：

> 铝矿 → 铝（工作温区 300 °C ~ 800 °C）

- 温度用 `GameUtil.GetFormattedTemperature` 格式化，跟随玩家的温度单位设置（℃／℉／K），不写死单位。
- 模板键 `STRINGS.UI.UISIDESCREENS.MATERIALOVERHAUL.RECIPE_TEMP_RANGE`，三个占位符为配方名、最低可工作温度、最高可工作温度。
- 没有温区数值的配方（其余精炼配方）名字保持原样。

## 6.3 配方详情面板的温度行

侧屏「配方详情」里的**效果**列表由 `SelectedRecipeQueueScreen.RefreshResultDescriptors` 取
`target.AdditionalEffectsForRecipe(配方)` 逐条生成，因此给 `ComplexFabricator.AdditionalEffectsForRecipe`
加后置补丁，为有温区数值的配方追加一行：

> 工作温区：300 °C ~ 800 °C（最佳温区 450 °C ~ 650 °C）

- 只对有温区数值的配方生效；`AdditionalEffectsForRecipe` 每次调用都新建列表，所以每次刷新只追加一条。
- 复用了原版的效果行 UI（`recipeElementDescriptorPrefab`），不新建界面元素。
- 温度同样走 `GameUtil.GetFormattedTemperature`。

## 6.4 温区输出端口的说明文本

原版 `BuildingLoader.InitializeLogicPorts` 在创建**建筑预制件**时就把 Def 上的端口描述复制给
`LogicPorts`（`outputPortInfo = def.LogicOutputPorts.ToArray()`）。那一刻本 Mod 的本地化键是否已建好不由我们保证：
一旦当时取到空串，这个端口在**整个游戏进程内**都没有说明文本，重新读档也不会变。

因此在 `LogicPorts.OnSpawn` 上加前置补丁，按当前文本重写端口标识匹配的 `inputPortInfo`／`outputPortInfo`
（`Port` 是结构体，用下标写回数组元素），并在命中时记录一条日志：

```
[MaterialOverhaul] MetalRefinery：温区端口说明已写入 —— 描述「温区信号」，激活「已锁定批次处于最佳温区」，非激活「未处于最佳温区，或没有已锁定批次」。
```

文本正确时是空操作；文本为空时修正。日志可用于确认端口说明是否真的写进去了。

## 6.5 与「明确说明状态」的关系

这些是**静态说明**，不是状态显示：它们不声称建筑正在生产或温度已经达标，符合「状态显示必须反映真实条件」的约定。真正反映当前状态的状态项（预热中、等待降温等）仍属后续版本。

# 7. 加热功率测试值

| 意图 | 功率 | 来源 |
| --- | --- | --- |
| 预热 | 1.2 kW | 用户给定：1200 W 用电按 1:1 换算为注热 |
| 补热 | 0.2 kW | 设计已确认的 200 W 额外用电，按同一 1:1 口径折算 |
| 强制运行持续加热 | 1.2 kW | 沿用预热值占位（该功率设计上属数值阶段） |

**这些是测试值，不是最终平衡数值。** 1:1 也只是测试口径，没有把「用电全部用于加热」定成正式换算关系。

已知限制：

- **注入热量不额外耗电**：建筑只要求「有实际供电」，预热期间不会在电网侧多扣功率（原版 `Operational` 只在生产且有人操作时置活动）。
- **预热耗时估算（计算值，未在游戏内实测）**：金属精炼器建造质量为 TIER5 = 800 kg，原版有效热容质量 = 800 × 0.2 = 160 kg；砂岩比热 0.8 → 约 128 kJ/K。从 300 K 升到启动阈值 573.15 K 需要约 273 × 128 ≈ 34,900 kJ，1.2 kW 约需 29,100 秒 ≈ 48.5 个游戏周期。**因此 1.2 kW 只适合验证机制，不适合作为正式数值。**

# 10. 风险记录

| 风险 | 说明 |
| --- | --- |
| 私有成员访问 | 订单流程读写 `nextOrderIdx`、`nextOrderIsWorkable`、`recipeQueueCounts`，并调用私有 `GetRemainingQueueCount`、受保护虚方法 `HasIngredients`。字段或方法名变化会让访问类型静态初始化失败（可定位，但会导致整批补丁装配失败） |
| 记账时机 | 批次完成的记账必须在前缀、计数同步必须在后置，顺序写反会出现「无限订单连做两批」或计数被扣两次 |
| 与其它 Mod 共存 | 其它 Mod 若直接改原版 `recipeQueueCounts` 而不经过三个公开入口，本 Mod 只能靠 `EnsureOrdersImported` 在下一次轮换前兜底 |
| 热阈值时刻 | 规则在 spawn 时应用；若建筑在应用前已经超温，原版过热判定可能按旧阈值触发一次 |
| 未接入额外用电 | 预热与补热目前不额外耗电，电网数据会偏低 |
| 描述文本重复追加 | `BuildingDef.Desc` 是计算属性，后置补丁每次取值都会执行；已用「包含即跳过」防止重复叠加，但若原版文案中恰好出现同一句会漏加 |
| 未做游戏内验证 | 部署已完成，但游戏内结论一条都没有，见 §8.2 |
