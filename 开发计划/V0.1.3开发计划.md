# V0.1.3 开发计划：数量点击与过热受损停热

2026-10-14，用户要求修复金属精炼器生产数量一次点击增加两批，以及强制运行过热损伤后继续加热至熔化的问题；明确授权更新版本、提交并推送 Git、重新部署。

## 1. 本轮确认的行为

- 「＋」一次只增加一批；保留独立订单身份和点击顺序。数量输入、减量、无限订单继续沿用原版入口。
- 强制运行在首次**实际过热扣血**后停止内置加热，并撤掉加热需求，不等生命值耗尽。仅越过过热阈值但尚未扣血时仍沿用强制加热。
- 停热保护复用当前损坏原因，直到完全维修才解除。降温、切换强制开关、换配方和读档不解除；部分维修仍停热。所有内置预热、补热和强制持续加热均服从这一保护，纯机械轻微损伤不触发它。
- 本轮停止的是内置加热，不新增强制生产的停机条件。生产继续服从原料、供电、自动化、操作、温度效率及生命值耗尽等现有条件，保留批次、进度、原料与损坏原因。
- 停止内置加热不关闭环境换热、原版过热损伤、材料相变或实际生产发热，也不在触发保护时重置温度。

## 2. 原版依据与问题定位

本轮从实际安装的 `E:\SteamLibrary\steamapps\common\OxygenNotIncluded\OxygenNotIncluded_Data\Managed\Assembly-CSharp.dll` 定向核对 `ComplexFabricator` 和 `BuildingHP`；`E:\ONI-Ref` 保持只读。

### 2.1 数量翻倍

原版 `ComplexFabricator.IncrementRecipeQueueCount` 先改计数、再调用 `RefreshQueue`。刷新中 `ValidateNextOrder → AdvanceNextOrder` 可能调用本 Mod 的 `RefreshNextOrder → EnsureOrdersImported`。已有其它订单、新配方暂不可执行时，会把刚增加的一批先纳入订单表；旧点击后置随后无条件 `AddBatchRequest`，于是同一次操作记两批。

本次用户运行日志存在铜配方原版数量 1 被迁入订单表的记录，与这条路径相符。复现采用实际数量补丁、同步与迁移源码，游戏对象用替身提供原版计数与刷新时序。

修正后，点击后置计算「原版当前计数 − 订单表合计」，只追加尚未入账的批次；已经迁入的新增数量不再次追加。不合并已有独立订单、不重写整个原版刷新流程。另修复同一刷新路径下数量 0 点「−」产生的临时无限值：原版计数和已迁入的临时订单同时清理，避免随后复活。

### 2.2 过热后持续加热

原门控只检查 `BuildingHP.IsBroken`，即生命值为 0；首次过热扣血通常仍有生命值，因此强制持续加热仍获许可。此前细节文档明确写着发生过热仍持续加热，本轮按用户新指示同步改为受损停热。

伤害补丁在原版 `BuildingHP.OnDoBuildingDamage` 前后比较 `HitPoints`；只有实际扣血且温度高于阈值、又不是本 Mod 机械磨损事件时才锁存过热原因。未实际扣血的无敌或空伤害事件不触发保护。沿用现有伤害来源识别口径，不重做其它伤害系统。

锁存原因后立即重新计算功率（`dt = 0`，不额外注热），撤掉加热需求与消费；加热许可层和耗电层都检查过热损伤。模拟步在判断加热前检查完全维修，恢复时按当前批次与开关重新判断。沿用现有序列化原因字段，不新增第二套安全锁存。
