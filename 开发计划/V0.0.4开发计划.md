### 1.3.1 一处被日志排除的误判（记录以免重复猜错）

审阅初稿曾把「本体温度在 **299.8 ℃ ↔ 305.5 ℃** 反复摆动、`允许生产 False, 加热 Preheat`」判为「开工线极限环」缺陷（预热顶到启动线就停机、开工资格又拿不到）。**该判断已被日志推翻**，此处保留结论以便后续不再重复排查：

- 日志显示同一栋建筑在 `16:40:46` 温度 **471.9 ℃** 时首次出现 `允许生产 True`。默认模式（主建造材料熔点 × 0.85、温区 300/450/650/800 ℃）**不可能**把开工资格卡到 470 ℃ 才给——该阈值只可能来自**控制模式的启动线 470 ℃**（`StartThreshold.Control`）。因此该存档的建筑当时处于**控制模式**。
- 在控制模式下，预热目标线就是 470 ℃。温度停在 300 ℃ 附近说明 1200 kW 的内置注热与建筑向环境散热的速度大致打平（每步注入 240 kJ、环境吸走约 226 kJ），**物理上到不了 470 ℃**，与启动线判定无关。日志最后升到 470 ℃ 以上是环境本身被加热的结果。
- 结论：`RunController` 的「低于启动线预热、到位后停止注热」不是缺陷，本版**不改预热与启动线判定**。同时这也说明 v0.0.3 的暂定注热倍率 1000 在保温差的环境里可能长期无法把建筑推到控制模式启动线，属**待用户决定的数值问题**，记在 §7。

# 2. 界面与开关的具体口径

## 2.1 建筑信息卡效果列表（本版最终内容）

按显示顺序，只保留以下条目；**不再包含**运行状态文字、订单列表、自造的当前／下一生产文案：

| 顺序 | 条目 | 条件 |
| --- | --- | --- |
| 1 | 工作温区行（工作温区 + 最佳温区上下限） | 当前配方有温区数值 |
| 2 | 当前生产：`Current order: <配方名>`，含批次进度 | 有已锁定批次（`CurrentWorkingOrder != null`） |
| 3 | 下一生产：`Next order: <配方名>`；无可执行订单时用原版 `No workable order` | 没有已锁定批次 |
| 4 | 功率行（请求功率／实际用电／实际注热） | 恒定 |
| 5 | 硬度行（主建造材料、硬度／要求硬度、生命值、磨损口径） | 恒定 |
| 6 | 过热「条件」行 | 本体温度超过过热阈值且尚未因此受损 |
| 7 | 原版 `Overheatable.GetDescriptors` 的过热温度行 | 本 Mod 在 v0.0.2 已实现，本版不动 |

规则与理由：

- 「当前生产」「下一生产」是**原版语义**的两个计划，不是本 Mod 的调度预告。原版 `NextOrder` 表示调度器接下来真正会执行的一批；配方名用 `ComplexRecipe.GetUIName(includeAmounts: false)`，与配方侧屏一致，因此也自动带上 v0.0.2 加的「工作温区」后缀。
- 没有已锁定批次但队列里还有订单时，`NextOrder` 可能为 null（全部缺料）——此时显示原版 `No workable order`，与配方侧屏表现一致；**不再**显示本 Mod 的「等待材料（待检查订单 N 笔）」，因为那是自造文案。
- 订单列表（逐笔一行、含 `▶` 当前标记）从信息卡**移除**。逐笔查看、加减数量、切换无限与取消仍在建筑详情面板的「材料革新：订单列表」侧屏里（v0.0.3 已交付，本版保留）。
- 效果列表里不再出现「预热中 / 生产已被自动化暂停 / 等待操作」等状态文字，这些改到状态栏（§2.3）。

## 2.2 建筑面板开关

| 按钮 | 本版处理 |
| --- | --- |
| 切换默认／控制模式 | **移除**（连同 `OnRefreshUserMenu` 里的按钮注册） |
| 开启／关闭强制运行 | 保留，行为不变 |

- 模式固定默认：`controlMode` 不再被任何界面改写；已有存档里 `controlMode == true` 的建筑读档后仍会是控制模式，用户无法再切回——因此**读档时把 `controlMode` 归为默认模式一次，并记录一条可定位日志**（迁移口径，避免存档把玩家永久锁在控制模式且没有入口）。
- 本地化键 `RUNMODE.TO_DEFAULT / TO_CONTROL / TOOLTIP_DEFAULT / TOOLTIP_CONTROL` 在 `ModStrings.cs` 与 `mod/strings/zh.po` 中**保留但不注册**（不删除键，避免以后恢复按钮时要重新写一遍；未注册的键不会出现在游戏里，也不会产生 `MISSING.STRINGS`）。
- 强制运行的文案与回差状态不变；其与模式组合的语义仍由 `RunPolicy` 承载。

## 2.3 运行状态改到状态栏

- 新增**本 Mod 专属的状态项类别**（不占用原版 `Main` 类别）：原版 `Main` 位置留给「操作任务」「损坏」等原版状态，本 Mod 的状态项与它们**并列显示**，互不覆盖。
- 状态项只在**有生产任务**时出现（有订单或已有锁定批次）。完全没有订单时，原版本来就显示「空闲」，本 Mod 不再追加一条「无生产任务」，避免同一信息出现两次。
- 状态名与 v0.0.3 的 `RunStatusText` 完全一致（预热中／补热中／持续加热／等待供电／生产已被自动化暂停／等待操作／生产中／低温低效生产／高温低效生产／高温保护／等待材料／损坏停机／手动禁用／降温中），组合规则不变。
- 状态项的提示文本给出同一步的真实数值：本体温度、温度效率、请求与实际电功率、实际注热、当前批次进度。数值全部读同一份运行数据，不是为了好看另算一份。
- 状态文字与提示都必须是本地化键（`STRINGS.BUILDING.STATUSITEMS.MATERIALOVERHAUL.RUNSTATUS.*`），并与 `mod/strings/zh.po` 同步。

## 2.4 自动化端口的悬停信息

- 两个端口都设 `displayCustomName = true`，使悬停卡标题使用端口自己的名称（温区输出＝「温区信号」，生产控制＝「允许／暂停生产」），而不是原版的通用 `INPUT`／`OUTPUT`。
- 输出端口悬停卡的内容按原版口径：标题 + `activeDescription` + `inactiveDescription` 两行已核实存在，本版保证在**实例生成后**它们的文本非空（v0.0.3 的 `LogicPorts.OnSpawn` 重写逻辑保留）。
- 复核 `LogicPorts.GetOutputValue`／`GetInputValue` 在端口列表为空时的空引用风险：原版这两处直接取 `outputPorts.Count` / `inputPorts.Length`，物理端口在 `OnSpawn` 之后才创建；本 Mod 的端口说明重写与信号发送必须**不早于**物理端口建立，避免端口存在但读值抛异常导致整张悬停卡不绘制。
- 端口位置**本版不改**：金属精炼器温区输出 `(2,3)`、生产控制输入 `(0,3)`，与 3×4 的 `PlacementOffsets`（x 为 0..2、y 为 0..3）及液体输入 `(-1,1)`、液体输出 `(1,0)` 均不重叠。
- **待游戏内确认**：D1 的确切表现（用户报告「完全不出悬停框」）。本版按「标题来源 + 说明文本非空 + 读值不抛异常」三条一起修，并在验收清单 G04 里逐项核对。

# 3. 预热与开工：本版不改

## 3.1 观察到的现象

金属精炼器本体温度在 **299.8 ℃ ↔ 305.5 ℃** 之间反复摆动，日志持续输出 `允许生产 False`、`加热 Preheat`，并成对出现「已撤销操作任务」与「已重建操作任务」。

## 3.2 核实过程与结论

1. 该存档的建筑处于**控制模式**。依据：同一栋建筑在 `16:40:46` 温度 **471.9 ℃** 时才首次出现 `允许生产 True`；默认模式的启动线是 315 ℃，不可能把开工资格卡到 470 ℃，只有 `StartThreshold.Control`（最佳温区下限 450 + 0.1 × 200 = 470 ℃）会给出这个阈值。
2. 控制模式下的**预热目标线就是 470 ℃**，而 300 ℃ 附近是建筑的散热平衡点：每 0.2 s 注入 240 kJ（1200 kW × 倍率 1000），与环境吸热大致相抵，因此温度在 300 ℃ 出头徘徊，**物理上到不了 470 ℃**。
3. `RunController` 的判定本身自洽：`Started == false` 且温度 < 启动线时持续给出 `Preheat`（299.8 与 305.5 两点都低于 470，意图都是 `Preheat`，与日志一致）；温度达到启动线的那一步会先置 `Started = true`，同一分支不会再回来，因此**不存在「到位即停机、资格又拿不到」的极限环**。
4. 结论：这是**暂定注热倍率 1000 与建筑散热之间的数值问题**，不是预热或启动线的逻辑缺陷。本版**不修改** `Heating/RunController.cs`、`StartThreshold.cs`、`HeatingPlanner.cs` 的任何判定；若要调整，属于用户对暂定数值的决定，见 §7 第 2 条。

## 3.3 由该结论带来的两项回归要求

- 默认模式（本版固定模式）必须能在常温环境中由 1200 kW 预热把建筑推过 315 ℃：验收 G06 用**默认模式**复核，若同样推不上去，则问题在注热倍率而不是启动线。
- 控制模式路径的数值与判定保持原样，只因为界面上不再有入口而不会被玩家触发。

# 4. 日志

- **本版不改日志判定。** D2 说明 `LogStateIfChanged` 输出的每一次都是**真实的状态变化**（温度确实跨过 300 ℃），把它过滤掉会让日志与真实状态不一致，违反「状态显示必须反映真实条件」的约定。
- 成对的「已撤销／已重建操作任务」同样是温度暂停机制在真实运作（每次跨线撤销、跨回重建），v0.0.3 §10.3 第 1 条已说明该实现的理由，本版不动。
- 若后续按 §7 第 2 条调整注热倍率，温度不再徘徊，日志量会自然下降，无需另加过滤规则。
- 状态栏的数据与日志共用同一步的 `RunDecision`，不额外扫描建筑（AGENTS 约定：不在每个模拟步全局扫描或输出日志）。

## 8.3 实现上的关键决定

1. **状态项不与原版重复**：已核实原版 `ComplexFabricatorWorkable` 的状态机本来就会显示 `FabricatorIdle`（无订单）、`FabricatorEmpty`（等材料）、`PendingWork`（等操作）、`ComplexFabricatorProducing`（生产中）。因此本 Mod 的状态项只承担**温度与自动化**造成的状态（预热／补热／持续加热／等待供电／高温保护／生产已被自动化暂停／低效生产）以及损坏停机与手动禁用；没有已锁定批次时不再重复这些原版条目。
2. **状态项用独立类别**：不用原版 `Main`，避免与「操作任务」「损坏」等原版条目互相覆盖（v0.0.3 的损坏原因沿用 `Main` 不变）。
3. **状态项按分类变化刷新**：只有 `RunStatusKind` 变化时才调用 `SetStatusItem`，不在每个模拟步重建界面对象。
4. **原版文案优先、内置回退兜底**：信息卡两行先取原版键；取不到时按当前语言回退到本 Mod 内置的中英文案，避免出现 `MISSING.STRINGS`。
5. **端口补丁改后置**：前置时物理端口尚未创建，`GetPortCell` 尚不可用且说明文本与端口状态可能不同步；后置既保证文本写入时机，也让日志能打印真实端口格子。

## 8.4 未做项与待用户决定

1. **预热与启动线判定未改**（§3 的核实结论）：日志显示的 300 ℃ 徘徊属控制模式预热目标 470 ℃ 与散热的数值冲突，不是逻辑缺陷。
2. **注热倍率 1000 是否够用仍待用户决定**（§7 第 2 条）。
3. **输出端口悬停的确切表现待游戏内确认**：本版改了标题来源、文本写入时机，并把端口格子写进日志；若 G04 仍然不出悬停框，需要按实测的端口格子与悬停判定继续排查。
