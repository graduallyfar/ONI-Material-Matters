# v0.0.1 开发文档

本篇记录 v0.0.1 的实现方式与待定项，只覆盖**底层系统**与**三个判断系统**：工作温区判断、预热判断、硬度判断。

机制含义以 [[2. 建筑系统设计细节]] 为准，本篇只说明怎么实现。**本篇不代替设计文档。**

---

# 1. 范围

## 1.1 本版做

| 模块 | 内容 |
| --- | --- |
| 工程骨架 | 可编译、可被游戏加载、日志可定位 |
| 温区判断 | 四边界结构、五态判断、效率函数（系数占位） |
| 预热判断 | 启动阈值、加热条件、热量注入（功率占位） |
| 硬度判断 | 主材料硬度取值、要求硬度比较、磨损累计（转换占位） |
| 订单最小部分 | 有序列表、轮换指针、锁定批次 |
| 持久化 | 订单、锁定批次、磨损等自有数据 |

**实现状态（本轮）：**以上模块均已落地，判断层在 `Core/`、`Zones/`、`Heating/`、`Hardness/`、`Orders/`，接入层在 `Game/`（建筑级组件 + Harmony 补丁 + mod 入口）。

强制运行与预热／补热的**判断部分**也已加入判断层：`RunPolicy`（模式 + 强制开关）、`TempZoneEvaluator.Decide`（模式只改变是否允许生产，不改变效率曲线；强制运行越界仍生产且保持对应侧边界效率）、`HeatingPlanner`（预热／补热／持续加热意图）。建筑组件已持久化模式与强制开关字段，但**面板开关与自动化接入属后续版本**，实际加热功率未定，尚未注入热量。

**两张侧表当前为空**：生效建筑名单只含《建筑分类与温区适用范围》§5 中已由代码核实的 5 个配方建筑，配方温区数值与要求硬度数值仍属待定项（§10 第 1、2、9 项）。因此现阶段的运行结果**应当与原版一致**，判断结论只通过日志体现——这不是缺陷，而是「未定参数一律占位」的执行结果。

## 1.2 本版不做

温度效率系数定案、加热功率与热量转换、磨损到伤害的转换、补热线具体位置、信息卡与状态栏、自动化输入输出、强制运行、电力系统、房间系统、辐射系统。

**本版不进行验证。**

## 1.3 实现原则

1. **不涉及原版机制。** 原版产热、过热损伤、批次结算、取料、运行状态判断全部保持原样，不接管、不包装、不替换。
2. **结构参考，函数重写。** 温区判断参考既有温度组件的存储结构与状态划分，但不调用其配置函数、不使用其状态机，判断函数与后果全部自写。原因见 §3.4。
3. **数值与机制分离。** 判断机制属于建筑级组件；四边界数值属于配方级侧表。
4. **未定参数一律占位。** 不把暂定值当作正式规则。
5. **白名单生效。** 只对明确列出的建筑启用，其余建筑行为等同原版。
6. **兜底不抛异常。** 配置缺失或校验失败时退化为原版行为，并记录可定位日志。

# 3. 温区系统

## 3.1 四边界与五态

温区由四个边界定义：

$$
T_{work,min}<T_{best,min}<T_{best,max}<T_{work,max}
$$

对应五态：

| 状态 | 条件 | 生产 |
| --- | --- | --- |
| 低于可工作温度 | $T<T_{work,min}$ | 停止 |
| 低温低效 | $T_{work,min}\le T<T_{best,min}$ | 效率下降 |
| 正常 | $T_{best,min}\le T\le T_{best,max}$ | 100% |
| 高温低效 | $T_{best,max}<T\le T_{work,max}$ | 效率下降 |
| 高于可工作温度 | $T>T_{work,max}$ | 停止，且停止内置加热 |

温度对象为**建筑本体温度**，不使用周围气体温度代替。

## 3.2 数据结构

```csharp
public struct TempZone
{
    public float WorkMin;   // 最低可工作温度
    public float BestMin;   // 最佳温区下限
    public float BestMax;   // 最佳温区上限
    public float WorkMax;   // 最高可工作温度
}
```

字段按**温度升序**排列。

> **注意构造顺序。** 既有温度组件的配置函数参数顺序是「低温警告、低温致命、高温警告、高温致命」，即低侧两项在前、高侧两项在后，**不是按温度升序**。本实现的结构体按升序排列，映射时须逐项对应，避免顺序错位。

`TempZone.Disabled` 为极宽区间，使判断恒通过、效率恒为 1，用于未配置建筑的退化行为。

## 3.3 温区与过热的关系

**温区上限与过热阈值无关，两者独立。**

| 机制 | 阈值 | 后果 |
| --- | --- | --- |
| 高温保护 | 最高可工作温度 $T_{work,max}$ | 停止生产和内置加热 |
| 过热损伤 | 建筑自身的过热阈值 | 原版机制，本版不改 |

过热阈值后续给出，与建筑相关。

### 3.3.1 必须核实的前提：过热开关现状

已实测的原版事实：

| 事实 | 数值 |
| --- | --- |
| 过热开关字段默认值 | `true` |
| 全文件中被**显式设为 `false`** 的位置 | **212 处** |
| 全文件中被**显式设为 `true`** 的位置 | **18 处** |
| 该字段的读取点 | 建筑组装阶段，条件成立时才挂载过热组件并写入过热阈值 |

**含义：大量建筑当前不参与过热损伤。** 因此对名单内建筑而言，温区上限**可能没有任何代价**——建筑因高温停产，但不会受损。

名单确定后必须逐个核对该字段现状：

- 若目标建筑设计意图是「高温有代价」，需要为其启用过热或提供等价的代价机制
- 若目标建筑本就豁免过热，须在设计层面明确温区上限是否仍要生效

**这是 v0.0.1 的前置核实项，不在本篇下结论。**

## 3.4 为什么重写而不直接复用

既有温度组件的结构如下，本实现参考其形态：

| 既有实现 | 本实现对应 |
| --- | --- |
| 五个温度状态枚举 | 五态枚举，含义一一对应 |
| 四个边界字段 | `TempZone` 四个字段 |
| 状态机按本体温度做参数转移 | 自建判断函数 |

**但不能直接复用**：其状态机在越界状态会执行角色死亡逻辑。建筑的越界后果是**停止生产**，不是销毁对象。因此：

- 不使用其配置函数
- 不使用其状态机
- 五态划分与边界语义参考，**判断函数与后果全部自写**

## 3.5 判断机制归属

温区判断机制属于**建筑级组件**，所有启用建筑共用同一份实现：

```csharp
TempState Evaluate(float bodyTemp, TempZone zone);
float     Efficiency(TempState state, float temp, TempZone zone);
```

组件**不关心四边界数值从哪来**。数值来源变化不影响机制层。

## 3.6 效率函数

分段形式：

- 低温段：随温度上升递增
- 最佳段：恒为 1
- 高温段：随温度上升递减
- 边界条件：最低可工作温度处取暂定值 0.3；最高可工作温度处取暂定值 0.8

**分段结构与边界条件可实现；各段系数为空函数占位，待数值阶段确定。**

## 3.7 边界校验

| 情况 | 处理 |
| --- | --- |
| 四边界交叉（如上限小于下限） | 退化为 `Disabled`，记录日志，**不抛异常** |
| 边界相等 | 视为合法，最佳段退化为一点，记录提示日志 |
| 数值非有限或非正 | 退化为 `Disabled`，记录日志 |
| 温度恰好等于边界 | 按五态表的开闭区间逐项判断 |

**校验失败退化为 `Disabled` 而非报错是刻意的**：宁可该建筑回到原版行为，也不能因它影响其他建筑。

# 4. 温区数值的来源

## 4.1 原版配方存储的实际情况

已核实的原版事实：

| 事实 | 结论 |
| --- | --- |
| 配方对象存放配方标识、输入输出、耗时、所属建筑、DLC 限制等 | 配方身份与材料信息完整可用 |
| 配方元素只含一个温度**操作类型枚举**（平均温度、加热、熔化、脱水） | 原版只有操作类型，**没有温度数值** |
| 任何配方元素构造器都不接受温度浮点参数 | 配方层无法承载温区数值 |
| 实际温度数值由建筑上的单个字段提供，仅部分操作类型读取 | **温度数值属于建筑，不属于配方** |
| 配方对象无序列化标记、非资源对象 | 配方不落盘，存档只存配方标识 |
| 配方对象运行时集中存放于配方管理器列表 | 启动后可枚举全部配方 |
| 配方标识由建筑名与输入输出材料名确定性拼接 | 标识**可读、可预测，可作为索引** |

**结论：原版配方数据结构里不存在「每个配方拥有自己的温度范围」的对应物。** 温区数值必须由本 Mod 提供。

> 原版存在若干与工艺相关的温度常量，但它们描述的是**产物温度**，不是建筑本体被允许工作的温度范围。两者不可混用，本版不采用它们作为温区数值。

## 4.2 采用方式

**复用原版配方标识作为索引，新增一张温度数值侧表。**

| 部分 | 归属 |
| --- | --- |
| 配方是什么、要什么材料、产出什么 | 原版，完全不动 |
| 配方标识 | 原版，直接复用，不新建 |
| 温区四边界数值 | 本 Mod 侧表，索引为原版配方标识 |
| 温区判断机制 | 本 Mod 建筑级组件，见 §3.5 |

**不新建平行配方系统。** 原版负责「有哪些配方」，本 Mod 只为每个配方标识记录一组边界数值。

## 4.3 侧表形式

```csharp
// 本 Mod 自有数据，原版类一字不改
Dictionary<string, TempZone> recipeZones;   // 索引 = 原版配方标识
```

- 侧表**不参与存档**，每次启动重建
- 未匹配的配方退化为 `Disabled`，并记录可定位日志

## 4.4 待定项

| 项 | 状态 |
| --- | --- |
| 侧表填入哪些建筑与配方 | 待定 |
| 各配方四边界具体数值 | 待定，本版占位 |
| 是否增加按材料的中间层以减少条目 | 待定 |

按配方标识直接填写时，部分建筑的配方数量较大（冶炼类建筑每种可冶炼矿物一条配方）。**这不影响 §3.5 的机制层。**

# 5. 预热系统

## 5.1 启动阈值

可从四边界直接计算：

- 默认模式启动阈值：最低可工作温度，加上「最佳温区下限方向区间」的十分之一
- 控制模式启动阈值：最佳温区下限，加上「最佳温区上限方向区间」的十分之一

**阈值公式属于已确认设计，可实现。**

## 5.2 加热条件

加热条件与生产许可分开判断：

| 条件 | 说明 |
| --- | --- |
| 存在已锁定批次 | 没有有效批次不加热 |
| 该批次材料齐备 | **已投料同样视为齐备** |
| 有实际供电 | 断电不加热 |
| 未被手动禁用 | — |
| 未因损坏停机 | — |

**判断条件完整实现。**

## 5.3 热量注入

- 注入的是**热量**而非固定温升，因此受建造材料热容影响
- 写入通过建筑本体温度接口进行，该接口具备无效值校验
- **注入量与功率转换关系为空函数占位**
- 因原版建筑产热逻辑保持不变（§1.3），此处只需处理**额外增量**，不接管原版产热

> **不使用固定温升代替加热。** 热量与温升的换算关系属于数值阶段内容。

## 5.4 补热

补热启动线与补热停止线**均取预热停止线**（已确认）。生产与补热可同时进行，补热不降低生产效率。

> **待确认的文档冲突。** 本节的「两条线取同一点（已确认）」与[[2. 建筑系统设计细节]]§2.1.2 的「补热启动线、补热停止线和生产恢复条件分别设定，避免在同一温度点反复启停。补热停止线高于补热启动线，两者都在最佳温区内部」不能同时成立：取同一点会在该温度反复启停。
>
> 当前实现按本节（同一点），但把两条线做成独立函数（`HeatingPlanner.TopUpLine` 与 `TopUpStopLine`），改为带回差的两条线只需改这两个函数。**以哪一处为准待确认。**

## 5.5 待定项

| 项 | 状态 |
| --- | --- |
| 加热功率与热量转换关系 | 空函数占位 |
| 建筑有效热容取值口径 | 待定，数值阶段处理 |
| 补热线随模式切换的具体取值 | 待确认 |
| 高温停机后的恢复位置 | 待定 |

# 6. 硬度系统

## 6.1 实际硬度取值

建筑实际硬度取**主建造材料**，辅料不参与：

| 步骤 | 方式 |
| --- | --- |
| 首选 | 建造记录中的第一个材料；原版惯例以索引 0 代表主体材料 |
| 回退 | 建筑本体元素；原版在建造记录缺省时也回退到本体元素 |
| 取值 | 元素的硬度字段，为字节类型 |

**取值方式完整实现。**

> 元素硬度字段为字节类型，取值范围有限。原版已定义语义化分级常量（极软、软、坚固、极坚固、近乎不可穿透、超硬、不可穿透）。要求硬度应直接使用这些分级，**不引入新刻度**。

## 6.2 要求硬度

**与温区侧表同构：索引为建筑标识，值为硬度分级常量。**

- 未匹配的建筑**不产生机械磨损**，行为等同原版
- 适用建筑采用明确名单，**不把所有工业机械套入同一规则**

## 6.3 磨损累计

| 规则 | 实现 |
| --- | --- |
| 按**实际生产时间**累计 | 磨损量随生产进度推进量增加 |
| 不按批次结算 | 长时间低效率生产累计更多 |
| 与加热状态**无关** | 单独预热或补热不累计 |
| 待机、等待材料、等待操作、暂停、禁用、断电、维修、损坏停机 | 不累计 |
| 生产与补热同时发生 | 只累计**一份** |
| 累计值类型 | 必须为浮点，**保留尚未形成整数扣血的累计部分** |
| 暂停、换订单、切换模式、取消订单、读档 | **不清除**已累计磨损 |

**累计逻辑完整实现。** 只有实际生产推进时才增加，因此磨损与温区效率之间自然保留联系。

# 7. 订单系统（最小部分）

## 7.1 为什么必须包含

**锁定批次是预热判断的前置条件**（§5.2）。没有锁定批次概念，预热判断无法成立，因此订单的最小部分属于本版范围。

## 7.2 改动范围

**只改订单判断，不改原版其他环节。**

| 保留原样 | 说明 |
| --- | --- |
| 批次结算 | 产物生成与结算沿用原版 |
| 取料 | 沿用原版取料流程 |
| 操作与状态机 | 沿用原版 |
| 运行状态判断 | **不挪用原版运行状态标志来表达温度停机** |

> 温度停产**不通过**原版的运行状态标志实现，避免与「缺输入」「断电」语义混淆。

## 7.3 判断模型

- 后端由「配方计数字典」改为**有序列表**
- **轮换只按材料齐备与否推进；温度不足不跳过订单**
- 已锁定批次在完成或取消前保持不变，其间指针轮换不改变它
- 材料齐备判断时，**输入存储与加工存储合并计算**
- 单一订单缺料时进入等待，不向后轮换
- 多订单建筑向复制人下达所有订单的取料指令，同一材料合并计算用量

## 7.4 与原版的差异

| 项 | 原版 | 本实现 |
| --- | --- | --- |
| 队列后端 | 配方计数字典，无顺序概念 | 有序列表 |
| 轮换位置 | 不存档 | 需持久化，见 §8 |
| 预取 | 为所有排队配方各预取固定批数 | 需重新对齐 |
| 温度参与判断 | 不参与 | 本版也不参与（预热另行判断） |

## 7.5 待定项

| 项 | 状态 |

| 侧屏界面 | 不在本版 |
| 预取策略的具体调整 | 待定 |

# 8. 持久化

## 8.1 数据归属

| 数据 | 存放 | 是否落盘 |
| --- | --- | --- |
| 订单顺序、剩余数量、轮换位置 | 本 Mod 自有字段 | 是 |
| 无限订单本轮进度 | 本 Mod 自有字段 | 是 |
| 当前锁定批次与目标温区 | 本 Mod 自有字段 | 是 |
| 已投入原料与生产进度 | 沿用原版 | 是 |
| 累计磨损 | 本 Mod 自有字段 | 是 |
| 温区四边界侧表 | 本 Mod 侧表 | **否**，启动重建 |
| 要求硬度侧表 | 本 Mod 侧表 | **否**，启动重建 |

## 8.2 旧存档兼容

**本 Mod 数据独立存放，不接触原版已有字段。**

- 不读取、不迁移原版的配方计数字典与上次工作配方字段
- 旧存档加载时，本 Mod 字段为默认值，视为「无本 Mod 数据」
- 建筑按原版行为运行，**存档不损坏**

## 8.3 读档校验

读取后需根据实际温度与供电重新校验运行条件，**不得**因读档重复投料、重复结算、清除磨损或重排订单。

# 11. 风险记录

| 风险 | 说明 |
| --- | --- |
| 三个系统相互耦合 | 磨损依赖生产时间，生产时间依赖温区效率，效率依赖批次锁定。三者同版本开发，问题可能累积到验证阶段才暴露 |
| 温区上限可能无代价 | 见 §3.3.1，大量建筑当前豁免过热 |
| 共享基类扩散 | 订单判断位于多建筑共用的基类上，必须依靠名单限定生效范围 |
| 私有状态访问 | 队列位置、取料额度、队列脏标记等在原版为私有，替换判断需访问，版本升级时易失效 |
| 新增配方静默落空 | 侧表未匹配时行为等同原版，缺少日志时难以发现 |
| 配方标识变体 | 配方标识存在带外观参数的变体形式，索引方式需覆盖 |
| 原版配方顺序 | 原版配方列表按排序字段与标识字符串排序，与玩家操作无关，替换后端时需注意 |
| 本版不做游戏内验证 | 判断层已有源码级测试（`tests\MaterialOverhaul.Tests`），但**游戏接入行为尚未在任何游戏内场景验证过**。本版不声称已通过运行验证 |
| 配方顺序记录依赖原版 UI 路径 | 本 Mod 的订单顺序只从原版入队 API（`IncrementRecipeQueueCount`／`SetRecipeQueueCount`）捕获，不经这两个入口的改动不会被记录 |
