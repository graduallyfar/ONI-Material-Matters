# V0.1.0 开发文档

本版目标：按 2026-10-12 的两张游戏截图和本次确认，收拢金属精炼器的界面信息；以温区输出端口是否接线决定默认／控制模式；继续定位并修复输出端口没有悬停框的问题；确保黑曜石作为与花岗岩同类的矿物原料参与建筑材料选择。

**当前状态：开发方案已编写，V0.1.0 尚未实现、构建、部署或进行游戏内验收。** 本次只修改文档，源码版本仍为 `0.0.4`。

- 编写日期：2026-10-12。
- 源码核查基线：本地提交 `952fb36`，开始工作时工作区干净；`MaterialOverhaul.csproj` 的版本为 `0.0.4`。
- 设计依据：[[2. 建筑系统设计细节]]、[[ONI Material  Overhaul Gameplay Design 总体设计]]。
- 历史实现：[[V0.0.3开发计划]] §10、[[V0.0.4开发计划]] §8。涉及界面和模式入口的冲突，以本篇及同步后的细节文档为准，不把前版的计划当作本版已完成结果。
- 本版仍以金属精炼器为验收对象，不扩大温区、硬度和内置加热名单。铝矿配方四边界、过热系数、功率、注热倍率和磨损数值沿用已有设计，本次不做数值平衡。

### 2.1 配置卡：只保留原版订单摘要

示意布局：

```text
配置
  当前安排：铝矿 → 铝
  下一安排：<原版当前给出的内容>
  配方
    铝矿 → 铝             <数量>

```

- 当前安排和下一安排继续由原版 `ComplexFabricatorSideScreen` 显示，两行各自读取 `CurrentWorkingOrder`、`NextOrder`；空值使用原版 `NO_WORKABLE_ORDER`，不另算一份预测队列。
- 不在建筑效果卡、状态卡或新建侧屏再复制这两行。原版配方详情中的安排生产量和持续生产按钮继续可用。
- 温度暂停后当前批次仍锁定，因此当前安排仍显示该批次；不能为了让界面看起来空闲而取消批次。

**实现位置：** `Game/Patches/OrderSideScreenPatch.cs` 当前在 `DetailsScreen.OnPrefabInit` 后追加 `MaterialOverhaulOrderList`。撤掉这项注册；`Game/OrderListSideScreen.cs` 不再创建实例。若没有其他引用，可在实现提交中删除这两个专用文件，不通过每次刷新后再强制隐藏来掩盖注册。

**保留订单机制：** `Orders/OrderQueue.cs`、订单持久化及 `Game/Patches/OrderPatches.cs` 继续负责添加顺序、重复配方、缺料跳过和无限轮次。移除的是逐笔可视编辑入口，不是把调度恢复为原版轮转。

### 2.2 移除逐笔界面后的操作边界

只剩原版界面后，玩家不能直接点选同配方的第 N 笔订单；本版接受这个界面取舍，不再补另一个订单列表。原版按钮仍按现有接入逻辑工作：

- `+` 经 `OnVanillaIncrement` 记录新增订单。
- `−` 经 `OnVanillaDecrement` 按现有回退规则减少该配方数量。
- 数量输入框／持续生产经 `OnVanillaSetCount` 处理合计数量：`0` 移除该配方全部订单，正数以对应有限批次数替换该配方订单，无限值替换为无限订单。直接设置合计数量会合并同配方多笔，这是现有行为；本版不把它描述成仍能逐笔编辑。
- 代码里的单笔订单身份和取消保护保留，不能为删侧屏而删掉当前批次取消、退料与防重复结算路径。

实施时重点回归原版按钮到订单表的链路。这里没有重新定义合计数量编辑如何重排同配方订单；如果现有行为与已确认订单顺序约束冲突，应记录为独立问题，不能借界面清理静默更换规则。

### 2.3 配方详情：温区唯一的数值说明入口

配方名称恢复为原版名称，例如 `铝矿 → 铝`。取消 `ComplexRecipe.GetUIName` 后置补丁附加的工作温区后缀，使配方列表、详情标题及当前／下一安排都恢复简洁。

有温区的配方在原版配方详情「效果」区域保留一条完整说明：

```text
工作温区：300 °C ~ 800 °C（最佳温区 450 °C ~ 650 °C）
```

- 继续使用现有 `ComplexFabricator.AdditionalEffectsForRecipe` 后置补丁提供描述。原版 `SelectedRecipeQueueScreen.RefreshResultDescriptors` 会读该列表，已有接入可复用。
- 取值来自**当前在详情中选中的配方**，不能取建筑正在生产的旧配方缓存。
- 没有温区配置的配方不追加数值，也不继承前一配方的温区。
- 温度仍经 `GameUtil.GetFormattedTemperature` 格式化，尊重玩家单位。
- 配方产物、用料、时间及原版配方热量继续显示；这里的「效果」是配方详情的区域，与建筑信息卡的「效果」分开处理。
- 建筑描述可以保留一句机制提示，并引导「具体工作温区见配方详情」；不再额外列四个数值，也不把该提示写成实时达标状态。

### 2.5 状态区域：模式、运行与损坏

状态分三类，互不覆盖：

| 类别 | 常驻文字示例 | 显示条件 |
| --- | --- | --- |
| 模式 | `运行模式：默认模式`／`运行模式：控制模式` | 已接入本 Mod 的适用建筑；无订单、断电和损坏时也显示 |
| 运行 | `预热中`、`补热中`、`等待降温`、`生产已被自动化暂停` | 按真实运行条件，与原版已有状态去重 |
| 风险与损坏 | `超过过热阈值`、`机械损坏`、`过热损坏`、`机械损坏＋过热损坏`、`损坏停机` | 分别依据实时温度、已锁存原因和建筑生命值 |

- 建议新增独立 `RunModeStatusItem` 及本 Mod 专属类别，在 `Db.Initialize` 后登记。不要把模式名仅拼进现有运行状态：现有运行状态在空闲时可能不显示，无法满足随时查看模式的要求。
- 默认模式的 tooltip 说明「温区输出端口未接线，在可工作温区内生产」；控制模式说明「温区输出端口已接线，只在最佳温区内生产」。两者都需注明仍受启动／恢复条件约束。
- 强制运行开启时，状态明确显示开启，并说明温区限制被覆盖；模式行仍报告接线决定的基础模式。关闭强制后按**当时的接线状态**重判。
- 运行信息复用 `RunStatusText`、`RunStatusItem` 的真实数据。审查 `ShouldShow` 与分类刷新条件，确保没有重复的「等待材料」「操作任务」「生产中」提示，也不因运行分类没变而漏刷模式。
- 硬度、主材料、磨损和生命值等详细说明可放入相关状态 tooltip；硬度不足但尚未受损只能提示磨损风险，不能写成已经机械损坏。无需新增一个“硬度合格”常驻条目。
- 超过阈值但尚未记录过热伤害，与已经过热损坏分开；不能把一次温度比较写成实际受损。已损坏原因降温后仍保留，直到本次维修按既定规则结束。
- 复用 `DamageStatusItems` 与 `MaterialOverhaulFab.Damage.cs` 的原因锁存。现有损坏项使用原版 `Main` 类别，实施时核对原版 HP 状态更新是否覆盖它；模式和运行不得占用 `Main`。只有复现相互覆盖后，才针对损坏条目调整归属或更新时机。
- 双重原因允许用一条文字同时写出两种原因，不要求人为拆成重复条目。维修温度处理仍按原因判定，不因移动显示位置而改变。

本次“损坏播报放在状态中”指建筑信息卡的说明归属；不为此全局关闭原版伤害动画、浮字、警报或其他建筑的状态。

### 2.6 黑曜石作为矿物原料建材

**用户追加确认：** 黑曜石可作为建筑材料，与花岗岩等归为同一类。这里的“同类”指建筑材料类别，不是将黑曜石的硬度、熔点、导热系数或比热容改成花岗岩数值。

**本机数据已核实：** 游戏安装目录 `OxygenNotIncluded_Data/StreamingAssets/elements/solid.yaml` 中，`Granite`（1018 行起）和 `Obsidian`（1449 行起）的 `materialCategory` 均为 `BuildableRaw`，两者也都具有 `BuildableAny` 标签。本地参考 `MATERIALS.ALL_MINERALS`／`RAW_MINERALS` 指向 `BuildableRaw`（624994 行附近）；`MetalRefineryConfig.CreateBuildingDef` 使用 `MATERIALS.ALL_MINERALS`（52108 行）。因此当前数据已经满足同类定义，不能把黑曜石写成原版尚不存在的新材料，也不应重复添加材料或重复注册标签。

实施时按以下顺序处理：

1. 核对实际运行时黑曜石元素的类别及建筑材料筛选结果，确保使用 `BuildableRaw` 类别的建筑能把黑曜石作为候选，至少验收金属精炼器和普通砖块。该建材规则不局限于温区建筑白名单，也不扩大温区或硬度机制的适用名单。
2. 若分类和候选本已正确，只补验证记录，不为完成条目制造无效补丁。若用户界面看不到黑曜石，先检查发现／库存条件、材料筛选和其他 Mod 的影响，不能直接判为类别缺失。
3. 若运行时确实缺少应有建材类别或本 Mod 错误过滤黑曜石，再在已核实的元素初始化／材料候选入口修复，保证幂等；仅补齐矿物原料建材资格，不把所有材料标签照搬自花岗岩，不放开金属、精炼金属等其他类别及建筑的明确材料限制。
4. 选用黑曜石建造后，主建造材料必须仍为 `Obsidian`，温区、过热阈值、热交换与机械磨损按其自身属性及现有规则计算；不改造已建成建筑的材料，不免费生成库存，不修改游戏安装目录里的 YAML 或程序集。

**状态：** 已完成本机静态数据核查；游戏内候选列表、建造与读档尚未验收。本条是否需要 C# 改动由上述运行核查决定。

## 3. 模式由输出端口接线决定

### 3.1 判定表

| 温区输出端口连接情况 | 输出值 | 基础模式 | 说明 |
| --- | --- | --- | --- |
| 未接线 | 红或绿 | 默认模式 | 输出逻辑仍按真实温区计算，未接线不等于取消该端口 |
| 已接线 | 红 | 控制模式 | 尚未达最佳温区或没有有效配方，不退回默认模式 |
| 已接线 | 绿 | 控制模式 | 温区满足，不代表已供电、有操作工或正在生产 |
| 仅输入端口接线 | 任意 | 默认模式 | 输入端的连接及红绿值均不选择模式 |

只检查 `TemperatureZoneSignal.PortId`，不用 `AutomationControlScope.PortId` 代替。不以 `GetOutputValue() == 1` 作为控制模式条件，否则温度变化会反过来切模式，改变已确认玩法。

已建成且覆盖端口格子的自动化线即按游戏的连接判定处理，不额外要求接到有效接收建筑、远端有电或信号为绿。规划蓝图不算已接线；断开远端但端口下仍留有线时，不应自行改成默认模式。具体连接时机以原版电路重建完成后的实测为准。

### 3.2 现有代码必须改的地方

1. 撤掉 `MaterialOverhaulFab.OnSpawn` 中无条件执行的 `MigrateControlModeToDefault()` 及“本版固定默认模式”迁移逻辑。保留序列化字段以读取旧存档，实际模式改由当前连接确定。
2. `OnRefreshUserMenu` 继续只注册强制运行按钮，不恢复手动模式按钮。
3. 新增局部方法，例如 `RefreshModeFromOutputConnection()`：确认建筑实例、目标输出端口、合法格子及电路管理器可用后，调用 `LogicPorts.IsPortConnected(TemperatureZoneSignal.PortId)`。
4. 只有连接决定的模式与缓存不同时，调用现有 `SetControlMode(bool)`，继而复用 `OnPolicyOrModeChanged()` 和 `RunController.OnPolicyChanged()`。不能每步重置 `runState`，否则会反复丢失补热或启动回差。
5. 在既有 `SimStep` 的运行判定之前刷新本实例的连接状态，再依次更新温区许可、加热、操作任务和状态。该步骤也必须在无订单、断电、手动禁用、损坏时运行，模式不能停留在旧值。
6. `OnPolicyOrModeChanged` 当前只是重建条件、标记队列和刷新菜单；实施时检查所有生产门控读值路径，确保本步不先拿旧 `runDecision` 推进生产或加热，再更新模式。

本地参考的 `LogicPorts.IsPortConnected` 通过端口格子查询 `logicCircuitManager.GetNetworkForCell`；并不要求读取输出的红绿值。其 `OnLogicNetworkConnectionChanged(int cell, bool connected)` 是私有回调，当前正文只更新缺线图标，**不能假设存在一个可直接订阅的同名 `GameHashes` 事件**。

**首选实现建议：** 在现有每次建筑 `SimStep` 中只查询本实例的一个端口，比较缓存后才处理变化。通常是既有约 0.2 s 步长，实际延迟需在游戏验证；这是局部常数次查询，不是全局扫描。若实测必须借助私有连接回调，窄范围后置补丁只把对应组件标记为待刷新，在网络更新完成后的模拟步再读最终状态，不在电路连接回调内部重入改网。

### 3.3 接拆线后的批次与温控

- 接线：默认转控制。保留当前原料、订单身份、生产进度、磨损余额和损坏原因，按控制模式重建启动资格、高温等待与补热状态。
- 拆除端口格子的线：控制转默认。保留同一批次，按默认模式重判，不继续沿用控制模式的补热目标。
- 温度在 350 ℃ 时，已经开工的默认模式可以低效生产；接线后控制模式应暂停并按已有启动线预热。
- 温度在 700 ℃ 时，默认模式允许高温低效生产；接线后控制模式进入等待降温，不制造主动制冷。
- 这些示例都受供电、自动化输入和其他开工条件约束；铝矿配方启动线仍沿用现有默认 315 ℃、控制 470 ℃，不把“进入最佳温区”误写成任何情况下立即恢复生产。
- 输入红信号下，连接输出仍可使建筑进入控制模式并预热／补热；输入红只暂停生产。
- 强制运行期间接拆输出线仍更新基础模式和状态行；关闭强制后按最新模式判断。输出信号一直按已锁定配方的真实最佳温区发送。

### 3.4 读档与初始化

连接状态属于电路现场事实，旧 `controlMode` 字段只能用于判断是否发生模式迁移，不能永久覆盖接线。

建议顺序：恢复订单／批次和温控存档字段 → 等待端口与电路网络可用 → 读取实际连接 → 校验模式 → 更新温控、门控和状态。

- 连接结果和存档模式相同：使用 `RunController.OnLoaded` 或等价的读档校验，保留合法的启动与补热回差；不要当作一次人为切模式重新从头预热。
- 不应未经检查就调用现有 `OnLoaded` 并宣称全部回差已保留：它当前会按高温暂停线重算 `HighTempWaiting`。实施时核对“已经高温暂停、读档温度位于恢复线与暂停线之间”的场景，应继续等待达到恢复线，避免读档提前恢复。
- 连接结果和存档模式不同：执行一次 `OnPolicyChanged`，并保存新模式；不清除批次、进度、损坏或磨损。
- 不在电路尚未重建时把“暂时查询不到网络”当作一次已确认拆线。初始化就绪点必须在目标版本核实；读档前几步的记录应能区分“尚未就绪”和“确实未接线”。
- 缺少应有输出端口时提供一次可定位警告，不静默声称自动切换已接入。
- 日志只记录初始化结果和实际模式变化：建筑 ID／格子、目标端口、连接状态、旧模式→新模式及触发原因。逐步查询不逐步刷日志。

## 4. 输出端口悬停修复

### 4.1 已核实与尚未核实

**本地原版代码已核实：** 自动化概览下，`SelectToolHoverTextCard` 遍历 `hoverObjects`，找到 `LogicPorts` 后调用 `TryGetPortAtCell(鼠标格子, out port, out isInput)`；命中才开始端口悬停卡。之后读取输入／输出值、标题和 `activeDescription`／`inactiveDescription`。

`displayCustomName == false` 时原版使用通用端口标题，并不是不绘制悬停卡。因此旧版把“未设自定义名称”直接列为“完全没有悬停框”的根因，证据不足。当前 v0.0.4 源码已经设置该标志并在 `LogicPorts.OnSpawn` 后重写说明，仍需按用户反馈继续核查。

另需更正旧说明：`GetPortCell` 按端口信息数组和建筑坐标计算格子，本身不需要物理端口列表；`GetOutputValue` 等读值路径才需要关注实际端口列表。`OnSpawn` 后置有助于保证初始化顺序，但不能单凭它证明鼠标命中或整个悬停流程正确。

**尚未核实：** 实际加载 DLL、鼠标格子是否进入该建筑的 `hoverObjects`、端口命中结果、是否存在数组／读值异常。本次没有启动游戏，也未读取这次截图对应的运行日志，不能断言单一根因。
