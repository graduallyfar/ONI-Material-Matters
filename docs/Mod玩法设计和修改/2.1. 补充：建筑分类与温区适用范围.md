# 1. 判定依据

## 1.1 原版已有的建筑类型标签

原版在 `RoomConstraints.ConstraintTags`（文件 `RoomConstraints` 类）中为建筑登记了房间约束标签，其中与工业直接相关的有：

| 标签 | 含义 | 用于 |
| --- | --- | --- |
| `IndustrialMachinery` | 工业机械 | 阻止房间获得房间加成；代码查询约 117 处打标签调用 |
| `GeneratorType` | 发电机 | 发电厂房间判定 |
| `HeavyDutyGeneratorType` | 重型发电机 | 发电厂房间的“调校”要求 |
| `LightDutyGeneratorType` | 轻型发电机 | 发电厂房间判定 |
| `PowerBuilding` | 电力建筑 | 电池等 |
| `WarmingStation` | 加温设备 | 空间加热器等 |

**`IndustrialMachinery` 是本 Mod 挑选工业建筑最可靠的原版口径**，因为它就是原版自己对“工业机械”的判定，并且已经生成在建筑 prefab 上，Mod 只需读取标签而不必维护另一份名单。

## 1.2 打标签位置

原版在建筑配置类的 `ConfigureBuildingTemplate` 或 `DoPostConfigureComplete` 中打标签，两种写法都存在：

```csharp
go.GetComponent<KPrefabID>().AddTag(RoomConstraints.ConstraintTags.IndustrialMachinery);
component.AddTag(RoomConstraints.ConstraintTags.IndustrialMachinery);
```

因此按类名匹配补丁不可靠（同一建筑可能在不同类中重复实现），**实现时必须按 prefab id 定位**。

## 1.3 原版已有的温度机制

| 机制 | 位置 | 现状 |
| --- | --- | --- |
| 过热阈值 | `BuildingDef.OverheatTemperature`（默认 348.15 K / 75 ℃），材料通过 `BuildingAttributes.OverheatTemperature` 修正 | 已存在，可按建筑单独设定 |
| 过热豁免 | `BuildingDef.Overheatable = false` | 已存在逐建筑开关，相当一部分工业与电力建筑已豁免过热 |
| 最低工作温度 | `MinimumOperatingTemperature` 组件，按`PrimaryElement.Temperature`与占位格温度判断 | 原版仅 2 处使用：IceCooledFan（273.15 K）、MassiveHeatSink（373.15 K） |
| 配方产物温度 | 配方建筑：`ComplexRecipe.RecipeElement.TemperatureOperation`（AverageTemperature／Heated／Melted／Dehydrated）＋ `ComplexFabricator.heatedTemperature`；连续转换：`ElementConverter.OutputElement.minOutputTemperature`／`useEntityTemperature` | 两条路径口径不同，取值方式见 §1.4 |
| 建筑自发热 | `BuildingDef.SelfHeatKilowattsWhenActive`、`ExhaustKilowattsWhenActive` | 已存在，可按建筑读取 |

**这意味着温区机制不必从零搭建：上限侧可直接复用 `OverheatTemperature`／`Overheatable`，下限侧可参考 `MinimumOperatingTemperature` 的判断方式，配方工艺温度可参考 `heatedTemperature`（该字段描述的是产物温度，不是建筑产热）。**

## 1.4 原版产物温度的取值口径

配方建筑的产物温度由配方元素自带的温度操作决定，`ComplexFabricator.SpawnOrderProduct` 逐产物赋值（181657–181737）：

| `TemperatureOperation` | 产物温度取值 | 代码位置 |
| --- | --- | --- |
| `AverageTemperature`（默认，多数配方） | 输入材料的质量加权平均温度，与建筑本体温度无关 | 181601–181639 计算，181668 赋值 |
| `Heated` | 建筑自身的 `heatedTemperature` 常量 | 181668 |
| `Melted` | 元素默认温度 `Element.defaultValues.temperature`，与输入温度、本体温度都无关 | 181728–181735 |
| `Dehydrated` | 脱水食物包装，按 `Heated`／`AverageTemperature` 同一逻辑赋值 | 181701–181727 |

`Heated` 使用的 `heatedTemperature` 以及各建筑自带的工艺温度常量如下，可作为配方温区的**原版依据**，而不是凭感觉分配：

| 温度 | 建筑 | 代码位置 |
| --- | --- | --- |
| 308.15 K（35 ℃） | DataMiner | 63414 |
| 313.15 K（40 ℃） | SupermaterialRefinery、WaterPurifier | 76209、79023 |
| 318.15 K（45 ℃） | AdvancedApothecary、CraftingTable、SuitFabricator | 1204、6285、75898 |
| 333.15 K（60 ℃） | FabricatedWoodMaker | 10735 |
| 346.5 K（73.35 ℃） | EthanolDistillery `OUTPUT_TEMPERATURE` | 10492 |
| 353.15 K（80 ℃） | Kiln | 46403 |
| 366.5 K（93.35 ℃） | EthanolDistillery `WASTE_OUTPUT_TEMPERATURE` | 10494 |
| 368.15 K（95 ℃） | CookingStation、Deepfryer、FoodDehydrator、GourmetCookingStation、Smoker | 5900、7130、39057、42529、72323 |
| 0（不加热） | FossilMine | 39546 |

同时存在与工艺相关的特征温度常量：

- `EthanolDistillery`：`CO2_OUTPUT_TEMPERATURE = 383.15f`
- `MethaneGenerator`：`CO2_OUTPUT_TEMPERATURE = 383.15f`、`WATER_OUTPUT_TEMPERATURE = 313.15f`
- `PeatGenerator`：`CO2_OUTPUT_TEMPERATURE = 383.15f`、`LIQUID_OUTPUT_TEMPERATURE = 313.15f`
- `MilkPress`：`OUTPUT_TEMPERATURE = 313.15f`
- `SpiceGrinder`：`OUTPUT_TEMPERATURE = 313.15f`
- `Desalinator`：`TARGET_OUTPUT_TEMPERATURE = 313.15f`
- `WaterPurifier`：`TARGET_OUTPUT_TEMPERATURE = 313.15f`
- `GlassForge`：输出熔融玻璃，`Melted` 温度操作（42400），温度取元素默认温度，不受建筑参数影响

**这一类只说明该建筑工艺涉及加热，不等于“建筑本体必须维持在该温度”。** 本 Mod 的温区是建筑本体温度，两者需要在参数阶段明确区分：`heatedTemperature` 描述的是产物带走的温度，温区描述的是建筑自身被允许工作的温度范围。

**金属精炼器不走上面的 `Melted` 路径。** 它使用 `LiquidCooledRefinery` 子类（`MetalRefineryConfig` 52128），在 `SpawnOrderProduct` 中把产物温度直接覆盖为字段 `outputTemperature`（默认 313.15 K／40 ℃，配置类未改写，197184、197271–197275），再按能量差把热量转给冷却剂（197276–197299，`thermalFudge = 0.8`，其中八成热量进入冷却剂）。因此精炼金属的温度既不等于矿石温度，也不是熔融温度：其配方本身标的是 `AverageTemperature`（52209），真实取值来自上述覆盖。

连续转换建筑（`ElementConverter`，即 §3 的 B 类）走另一条路径，逐输出口由 `OutputElement.minOutputTemperature` 与 `useEntityTemperature` 决定（构造函数 265192，取值 265691）：`useEntityTemperature = true` 时使用建筑本体温度；否则取 `max(minOutputTemperature, 输入材料平均温度)`，即该参数是下限而非定值；两者都为 0 时改用建筑本体温度，效果等于跟随输入温度（脱盐器、净水器等即此写法）。

**热量是否结算：** 除 `LiquidCooledRefinery` 外，`SpawnOrderProduct` 与 `ElementConverter.ConvertMass` 都只直接赋值产物温度，不结算能量，温度-能量换算在原版产物流径上只出现在精炼器冷却剂一处（197276、197323）。也就是说原版把产物加热到 `Heated`／`Melted` 温度时，这部分热量是凭空产生或消失的。

**以上都是原版机制记录，不是本 Mod 已确认规则。** 本 Mod 暂不为产物温度单独设定口径，沿用原版取值，温区只约束建筑本体温度；产物温度是否需要与本体温度挂钩、产物温升是否需要从建筑热账扣减，仍属未定项，见 §5 第 7 项。

## 1.5 温度区间与过热阈值的现状

**v0.0.2 逐个复核了目标版本各配置类的 `CreateBuildingDef`：名单内建筑并不能按分类推断，必须逐项核对。** 结果分三类：

| 过热现状 | 建筑 |
| --- | --- |
| **显式豁免**（`Overheatable = false`） | 窑炉、藻类蒸馏器、堆肥、乙醇蒸馏器、氧石精炼炉、铀素离心机、制冰风扇、液冷风扇 |
| **参与过热，阈值取默认 348.15 K（75 ℃）** | 金属精炼器、玻璃熔炉、岩石粉碎机、漂白石脱离机、肥料机、净水器、脱盐器、原油精炼厂、聚合物压塑器、化学精炼厂、分子熔炉、钻石压机、橡胶制造机、污泥压滤机、乳脂分离器、植物粉碎机、制冰机、融冰壶、制冷机、石油发电机、人造木材机、巨型散热板 |
| **参与过热，另有更高阈值**（398.15 K / 125 ℃） | 液体加热器、空间加热器、液体冷却器 |

> **修正记录：** 本节早先把金属精炼器、玻璃熔炉、岩石粉碎机、漂白石脱离机、肥料机列为豁免过热，与目标版本程序集不符——这些建筑的配置类没有写 `Overheatable`，取的是 `BuildingDef` 默认值 `true`。真正豁免的是上表第一行。

> **2026-10-16 定向复核：** 实际安装的 `UraniumCentrifugeConfig` 显式设 `Overheatable=false`，已补入上表；新23栋方案中该建筑与乙醇蒸馏器、藻类蒸馏器、氧石精炼炉建议保留豁免，尚未由用户审阅定案。油井 `OilWellCapConfig` 的原版基础过热温度为2000 ℃，不适用上表的默认75 ℃；其材料上限替换也是新增方案的一部分。

**接入温区时需逐栋核对生产门控与过热伤害。** 已参与过热的建筑更新阈值；原版豁免过热的候选，是否启用伤害组件必须在该建筑接入前明确，不能仅因列入候选名单就自动改动。窑炉已由用户确认为保留豁免：本体工作上限单独计算，不新增过热组件或过热伤害。普通模式超过材料上限停产停热；强制越界才允许继续生产，停产本身不免除环境过热伤害。

> **v0.0.2 历史实现：** 金属精炼器曾按「主建造材料熔点 × 85%」改写过热阈值，并使用炼铝 300／450／650／800 ℃四边界；能否承受该温度取决于具体建材，不能据此声称所有材料均能安全覆盖整个区间。**V0.1.2 设计改为 75%，建筑上限与过热阈值合并，配方仅保留最佳区。** 最新设计见[[2. 建筑系统设计细节#2.1.5 过热阈值与主建造材料]]，实现与验收状态另见 [[V0.1.2开发计划]]；上表仍是原版事实，不是 Mod 改造后的统一状态。

# 2. 建筑分类（按是否需要温区）

## 2.1 分类框架

| 类别 | 判定特征 | 是否加温区 | 理由 |
| --- | --- | --- | --- |
| **A 配方生产类** | 含 `ComplexFabricator`／`ComplexRecipe`，有配方队列与投料，一次生产有离散进度 | **是，建筑工作范围＋配方最佳区；新效率曲线待定** | 生产是离散批次，温度可以表现为进度变慢与暂停；建筑范围不随配方改变，普通控制生产使用两区交集 |
| **B 连续转换类** | 含 `ElementConverter`＋`ElementConsumer` 或导管输入输出，按 kg/s 连续处理 | **温度效率影响每秒处理量（2026-10-16 已确认，未实现）** | 原料消耗与全部产物生成同比例乘温度效率，保持转换比例；不建立批次进度与订单队列，具体名单和参数逐栋确定 |
| **C 热管理类** | 专门制热／制冷：`SpaceHeater`、`LiquidHeater`、`AirConditioner`、`LiquidConditioner`、`IceCooledFan`、`LiquidCooledFan`、`IceMachine`、`IceKettle`、`ThermalBlock`、`MassiveHeatSink` | **建议只设本体温度上限，不设工艺温区** | 它们的“工艺”就是热量搬运，本身不产出配方产物。对它们设温区等于让加热器因为太热而停机，需要单独判断是否合理 |
| **D 电力类** | `GeneratorType`／`PowerBuilding`：发电机、电池、变压器、电线 | **发电机建议纳入，输配电不纳入** | 发电机有燃料消耗、自发热与发电厂房间加成，纳入后与温控、房间系统都能连线。电池与电线本身不生产，纳入会让玩法变噪 |
| **E 物流与管路类** | 各类 Conduit、Bridge、Valve、Pump、Vent、Reservoir、BottleEmptier、Solid 传输 | **不纳入** | 属基础设施，无生产批次。注意原版把它们中的一部分也标了 `IndustrialMachinery`（气泵、液体泵、过滤器、排放口、固体过滤器等），标签与“是否需要温区”不是同一个口径。`AutoMiner` 不带该标签，但按功能同属本类 |
| **F 农牧与生命维持类** | 农场砖、种植盆、孵化器、孵化站、喂食器、动物居所、电解器、除碳器、矿物除氧器 | **暂不纳入** | 属生物与环境过程。2026-10-16用户已将净水器、脱盐器、氧石精炼炉明确纳入后续工业处理名单，按B类设计，仍未实现；其余边界见 §4 |
| **G 生活、医疗、研究、装饰、自动化、火箭、结构类** | 床、餐桌、厕所、淋浴、按摩、医疗站、研究站、望远镜、灯、画、雕像、逻辑门、传感器、火箭部件、门、梯子、砖块 | **不纳入** | 无机械负载，与“材料硬度／温区”两条线都不相关 |

## 2.2 分类结果与原版标签的对应关系

- 原版 `IndustrialMachinery` 标签：完整匹配 `AddTag(RoomConstraints.ConstraintTags.IndustrialMachinery)` 的调用共 117 处。按配置类归属去重后，本篇实际列出 **96 个建筑**；差额来自同一建筑在不同配置类中重复实现（`AdvancedApothecary`、`Desalinator`）以及一处尚未定位归属的调用（文件 184302 行以外另有 1 处待核对）。**完整去重总数在编号阶段复核，不影响分类框架。**
- 其中属于 E 类（不需要温区）的共 16 个：`GasPump`、`GasMiniPump`、`GasFilter`、`GasVent`、`GasVentHighPressure`、`GasBottler`、`BottleEmptierGas`、`BottleEmptierConduitGas`、`LiquidPump`、`LiquidMiniPump`、`LiquidFilter`、`LiquidVent`、`SolidFilter`、`GasReservoir`、`LiquidReservoir`、`LiquidBottler`。
- 属于 C 类（热管理）的 9 个：`AirConditioner`、`LiquidConditioner`、`IceCooledFan`、`LiquidCooledFan`、`IceMachine`、`SpaceHeater`、`LiquidHeater`、`MassiveHeatSink`、`IceKettle`（后两者不带该标签，按同类处理）。
- 属于 A／B 类（生产）的 **67 个**，是首批温区设计的主要对象。
- 属于 D 类（发电）的 7 个：`Generator`、`PeatGenerator`、`HydrogenGenerator`、`MethaneGenerator`、`PetroleumGenerator`、`WoodGasGenerator` 带 `IndustrialMachinery`；`ManualGenerator` 只带 `GeneratorType`／`LightDutyGeneratorType`，需单独加入。
- `SteamTurbine` 带该标签，`SteamTurbine2`（`SteamTurbineConfig2`）不带。两者都在 §4 单独审阅。

# 5. 进入首批温区设计的范围（待确认）

**原建议首批范围：A 类 24 个＋B 类 11 个＋D 类 7 个＝42 个建筑。** 2026-10-12 纠正两项分类并补入此前文字中已提到但表格遗漏的铀浓缩离心机后，当前候选表为 A 类 27 项＋B 类 9 项＋D 类 7 项＝43 项；这是本篇候选表计数，不是全游戏去重总数，也不代表全部已授权开发。本次用户确认先设计其中的工业批次建筑，具体 13 栋与配方范围见 [[4. 工业配方建筑数值设计]] §1.1。

理由：

1. A 类是“温度影响工作时间”模型的天然对象，与总体设计第 2.1 节的思路一致。
2. D 类发电机的加入使温区系统与[[#3 电力系统]]以及发电厂房间产生横向联系，符合“不增加纵向玩法、增加横向联系”的原则。
3. B 类已确认以温度效率缩放每秒处理量，原料与全部产物同比例变化；下一步逐栋确定温区、效率参数和运行条件，不再把速率语义列为未定。
4. C 类热管理设备与 E 类基础设施建议整体排除，避免让加热器因为过热而停机这类反直觉结果。
5. `NuclearReactor`、`SteamTurbine`、`SteamTurbine2` 已经是原版温度相关建筑（有独立效率与过热逻辑），应先单独审阅再决定，不并入首批。

**名单核实进度：**本次范围内的 13 个 A 类工业候选已逐项读取本机配置，窑炉、岩石粉碎机等不再仅为功能推定；此前的候选核实不等于全部接入；当前源码明确白名单为原六栋加第三批23栋，共29栋（第三批已部署，尚未游戏验收）。B 类原有核实记录中，净水器、乙醇蒸馏器、脱盐器的连续转换分类保留，漂白石脱离机原核实结论已纠正。其余建筑是否进入开发仍需按系统逐项确认，不能把整张候选表视为已实现范围。

**尚待确认的问题（未定，不影响先做已核实的生产建筑）：**

1. B 类的处理速率语义已确认；各栋建筑的温区、效率参数、耗电、自热和预热能力仍待逐项设计。
