# V3.0.0 开发计划：房间系统

编写日期：2026-10-19。设计依据：[[4. 房间系统设计]]，系统定位见 [[ONI Reform 总体设计#4. 房间系统]]。

**状态：开发文档已整理，房间代码未开始。** 本次完成范围拆分、目标游戏首轮核实、实施顺序、未决事项及验收清单。尚未构建房间版本、部署或运行游戏，也未完成平衡验收。`V3.0.0` 沿用总体设计的系统里程碑名，不代表已确定房间独立版发布号，不修改现有版本元数据。

工作分支：`codex/room-system`，从 `codex/power-system` 的 `4c20bc6` 创建。该基线包含工业与电力代码及三种隔离构建；源码存在不代表应在房间独立验证时启用它们。当前工程仍只接受 `Industrial`、`Power`、`Combined`，默认 `Power`，**尚无房间构建模式**。已有交付见 [[V0.2.2开发计划]]、[[电力V0.0.2开发计划]] 和 [[系统隔离验证记录]]。

## 1. 目标与实施范围

让房间构成、平均装饰度和平均温度成为工程条件，提供分设计已列明的生活、娱乐、工业、医疗、科研及航天加成。保留 T1 开局体验，复用原版房间识别、建筑使用、属性效果与分配机制。

### 1.2 边界

- T1 的公共厕所、卫生间、宿舍、食堂不新增条件或改变加成；未列出改造规则的原版房间不顺带改数值。
- 不新增设施、配方、科技或整套特质生成系统；房间使用现有建筑。特质定义不足时先完成不依赖该定义的工作。
- 不改复制人周期装饰感知算法；房间环境是独立条件，不更改建筑本体温区、内置加热、强制运行、自动化、磨损或维修规则。
- 工业区不直接复用工业温控的 29 栋白名单作为已确认名单；原版「工业机械」标签与本设计的「工业建筑」是两种用途。
- 房间独立验证不启用工业或电力系统。整合阶段再验证既有系统交互；不提前加入辐射耗散系统。医疗中心的辐射病救治属于本篇明确列出的房间效果。

## 2. 原版核实与接入依据

### 2.1 本轮核实范围

本轮只读反编译本机安装的 `E:\SteamLibrary\steamapps\common\OxygenNotIncluded\OxygenNotIncluded_Data\Managed\Assembly-CSharp.dll` 中相关类型，并读取同一安装的 `StreamingAssets\Tuning.json`；未修改游戏或 `E:\ONI-Ref`。程序集 SHA-256：

```text
A58E04D0FFDF89B86FB28B71AD900625B3B539DB30D67F8C6269F73A9F5AE599
```

`KleiVersion`：`ChangeList=744825`、`BuildBranch=release`。参考代码仅用于 `rg` 定位；下表结论来自本机目标反编译结果。反编译临时文件位于忽略目录 `_build/room-doc-reference/`，不分发、不提交，不作为运行依赖。

| 入口 | 已核实行为 | 对实施的约束 |
| --- | --- | --- |
| `Db.Initialize()`、`Database.RoomTypes(ResourceSet)` | 初始化房间分类及类型，构造各房间的主条件、附加条件、升级路径和效果 | 在房间表存在、首次房间探测前登记；实施时核实补丁时序和幂等性，不在每次刷新重复登记 |
| `RoomType` 构造函数、`isSatisfactory(Room)` | 主条件不满足与附加条件不满足返回不同状态；构造函数同时接收 `priority`、`upgrade_paths`、`effects` 等 | 保留原版对象的 ID、未修改条件和升级关系；变更不可只修改显示文本 |
| `Database.RoomTypes.GetRoomType(Room)`、`HasAmbiguousRoomType(...)` | 同时检查优先级、升级路径、主条件及 `stomp_in_conflict`；冲突可能回到 `Neutral` | 必须列出新旧房间的冲突矩阵；不能仅按 T1–T3 排一个数字优先级 |
| `RoomConstraints.Constraint.isSatisfied(Room)` | 可组合建筑谓词与房间谓词，按数量检查 `room.buildings` 和植物 | 复用原版判定结构；新增环境条件应共用缓存，不让每个候选房间重复扫描格子 |
| `RoomConstraints.LIGHT` | 已标记废弃，保留项的建筑与房间谓词均为空，不能检查灯具 | 不直接复用此项实现光照要求；按 D06 确认后的灯具／照明语义建立真实条件 |
| `RoomProber.RefreshModule.AddRoomContentsToCavities()`、`RefreshRooms(...)` | 超过 `maxRoomSize` 的 cavity 跳过内容收集和普通房间创建；本机 `Tuning.json` 上限为 **128 格** | 1000／2400／360 格设计无法只靠放宽单个 `RoomType` 尺寸实现，须先解决大房间接入 |
| `CavityInfo.cells`、`NumCells` | 保存 cavity 实际格子集合，`NumCells` 是其数量 | 使用实际格子，不能以外接矩形面积代替；分裂、合并后句柄与集合会变化 |
| `RoomProber.IsCavityBoundary(int)` | `Solid`／`Foundation` 标记或门构成边界；房间刷新默认忽略门开关引起的实体变化 | 复用原版封闭区域定义，不能把开门直接解释成房间合并；超大开放区域与太空发射平台须专项验证 |
| `RoomProber.UpdateRoom(CavityInfo)` | 清理旧房间、创建新房间、重分配建筑，向建筑和植物发送房间更新事件 | 环境失效重判会有分配和事件副作用，不能每次采样无条件重建 |
| `RoomTracker.IsInCorrectRoom()` | 比较 `room.roomType.Id == requiredRoomType`，不自动认可升级房间 | 地质研究室等升级款需要核对建筑原有房间许可；不能无条件放宽所有 `RoomTracker` |
| `RoomType.TriggerRoomEffects(...)` | 由主条件匹配的触发建筑把 `effects` 加到目标复制人 | 登记效果不等于会触发效果；需核实每种建筑的实际使用链和时机 |
| `RoomMonitor`、`CavityInfo.OnEnter(...)`、`ParkSign.TriggerRoomEffects(...)` | 复制人路径推进时发现房间变化，通知室内建筑；公园标识据此触发房间效果 | 可参考人造公园的进入触发，但房间重建时的静止复制人仍需复核，不能据此统一其他房间的触发方式 |
| `LegacyModMain.ConfigElements()` | 为元素添加 `AttributeModifier("Decor", ..., is_multiplier: true)` | 材料装饰度有原版属性入口；登记要按目标项更新并保持幂等，不覆盖无关修饰项 |
| `DecorProvider.AddDecor()`、`Refresh()`、`GameUtil.GetDecorAtCell(...)` | 提供者把可见范围内的贡献加入 `Grid.Decor`；`GetDecorAtCell` 可另含光照装饰，并对实心格返回零 | 地板贡献可能已在采样值中；下方一格的附加项、光照项与去重口径须明确 |
| `BuildingComplete.OnSpawn()` | 存在将 `Deconstructable.constructionElements` 中辅料元素／预制件修饰项加入建筑属性的路径 | 装饰度不能未经核实就套用硬度系统“只取主材”的口径，还需追踪主材修饰链 |
| `DecorMonitor.Instance` | 按时间累计感知装饰度，周期结算 | 房间判定不写入其累计值、不修改周期效果阈值；材料改动导致感知输入变化属于另需验证的实际结果 |
| `MissionControlClusterConfig`、`MissionControlCluster.Instance.UpdateWorkableRocketsInRange(...)` | 群星指挥站属 `EXPANSION1`，原版配置已有速度倍率；范围筛选使用半径常量值 | 须区别“新增加成”和“原版总效果”；仅改配置常量不保证改变已编译的调用 |
| `GeoTuner.Instance`、`GeoTunerConfig` | 保存分配的喷泉和调谐修正，要求 `RoomTracker`；配置有调谐数量上限 | 产量、数量限制、原版温度修正与 UI 要分别追踪，不能只修改一个静态值就称全部生效 |
| `DataMinerConfig.GetRequiredDlcIds()`、`DataMiner.ComputeWorkProgress(...)` | 数据挖掘中心依赖 `DLC3`；进度已有按建筑本体温度计算的 `EfficiencyRate` | 房间低温与建筑自身效率是两个量；独立房间加成不能替换原版温度效率或重复推进进度 |

原版已有 `PrivateBedroom` 字段的实际 ID 为 `"Private Bedroom"`，宴会厅 ID 为 `"BanquetHall"`，医院为 `"Hospital"`。登记前按 ID 核对，不用中文显示名猜 ID。新房间应使用本 Mod 命名空间下的稳定 ID，具体名称在实现时统一确定。

## 3. 实施前需要确认的规则

本节把分设计 §4.4 的未决事项展开为可执行的确认清单。**下列问题不在本文中替用户定案。** 每项确认后先回写分设计有效段落，再更新本节状态；不把开发建议当成已确认规则。不依赖该问题的基础调查、判定结构和验证方案可以先推进。

| 编号 | 待确认事项 | 需要形成的明确契约 |
| --- | --- | --- |
| D01 | 等级和名称 | 对齐公园／自然保护区的 T2、T3 重复，补齐 T3 总清单；确认“私人宿舍”对应私人卧室，“舞厅／歌舞厅”“展览馆／博物馆”是同一对象的称呼，不额外新增房间 |

| D03 | T3 通用装饰度的例外 | 分设计称所有高级房间均需最低装饰度，但航天发射场、星际货运站、数据机房未给阈值；明确例外或补阈值，不默认套用其他房间数值 |

| D13 | 特质定义与接入来源 | 护理员和六项娱乐偏好特质的稳定 ID、已有／新增身份、获得方式和互斥关系；两类海滨特质并存时取哪组效果；不以“理论艺术家”“气球艺术家”替代“艺术家” |

| D15 | 发射与货运效果生命周期 | 火箭加成在停靠、发射、飞行或回航的哪一阶段生效，换平台与多房间是否叠加、燃料折扣扣在哪一步；货运“载货速度”“发射次数”的实际含义以及清理中断／重建后的进度 |

## 4. 技术实施方案

本节为开发方案。文件名是建议落点，**尚未创建对应源码**；玩法参数、名单与效果持续时间以 §3 确认后回写的分设计为准。

### 4.1 配置、判定、游戏接入和显示分离

| 层次 | 建议位置 | 职责 |
| --- | --- | --- |
| 房间配置 | `MaterialOverhaul/Rooms/RoomCatalogue.cs` | 集中维护稳定房间 ID、构成、环境阈值、效果引用、DLC 条件与经确认的升级／冲突关系 |
| 分类配置 | `MaterialOverhaul/Rooms/RoomBuildingCatalogue.cs` | 明确设施与工业建筑等名单，不以共享组件自动扩大范围 |
| 纯判定 | `MaterialOverhaul/Rooms/RoomEvaluator.cs`、`RoomEnvironment.cs` | 输入房间快照，输出满足状态、缺失项、平均环境值和效果资格；不读 Unity 全局、不结算生产 |
| 登记与生命周期 | `MaterialOverhaul/Game/RoomRegistration.cs`、`RoomEnvironmentMonitor.cs` 及局部补丁 | 登记类型、缓存与更新环境、处理分裂合并、给受影响建筑发送更新；未知类型提供可定位日志 |
| 效果接入 | 按生产、娱乐、医疗、科研／航天分别放置组件和补丁 | 在真实使用或结算链中应用修正；登记条件与实际效果分开验收 |
| 本地化与显示 | `RoomStrings.cs`、`RoomText.cs`、`mod/strings/zh.po` | 房间名称、条件、当前环境、未生效原因和效果说明；字段注册、中文 PO 和备用文本同步 |
| 验证 | `tests/MaterialOverhaul.Tests/` 与既有 Profile 检查工程 | 判定、生命周期、各效果边界和实际 DLL 隔离；仅在实现对应模块时增加相关测试 |

不引入通用规则引擎或新前置库。以具体房间和经核实的入口做小范围接入；主材、热量、订单和磨损继续由现有系统负责。

### 4.2 超过 128 格的房间

1. 保留工业区、航天发射场、星际货运站的既定尺寸，不为适应原版探测上限而缩小它们。
2. 先做大房间接入验证：核实运行期调优值能否在初始化前安全扩容，并配合新增类型自己的尺寸条件。不能只改 `MAXIMUM_SIZE` 条件；也不能只在候选判定时伪造内容，绕过原版建筑分配与事件。
3. 如果扩容会使无关区域创建额外普通房间、改变养殖拥挤度／房间显示或显著放大内容收集成本，则改为只识别明确候选区域的局部接入，并重新核实建筑／植物更新链。方案按证据选择，不对共享探测器无条件放宽全部房间规则。
4. 必须验证最小尺寸、原版 128 格边界、各房间设计上限及上限外一格；开放洞穴、跨世界、火箭内部和太空发射平台不得被误认。保留原版房间自身的大小条件。
5. 记录每次拓扑变化涉及的格子数与候选数，在专门测试档观测大殖民地开销。通过前不把“大房间支持”标为完成。

### 4.3 平均环境与动态重判

- 以 `CavityInfo.cells` 建立拓扑快照；环境缓存按世界、有效 cavity 及本次拓扑身份区分。读档后重新建立，不把旧房间对象或句柄永久序列化。
- 建筑增减、植物变化、作品／藏品替换等结构变化使相关区域失效；温度和装饰变化还需独立的环境更新渠道。不能认为原版建筑变更事件会覆盖气体温度变化。
- 先按 §3 的采样契约计算房间平均值，再统一提供给所有条件和显示。显示值不能采用另一套四舍五入后参与比较；摄氏显示与 K 存储只做一次一致换算。
- 对有环境条件的候选区域分批更新，避免每个模拟步全图扫描；同一轮一个区域最多计算一次共享快照。更新频率待确认，不用不可见的延迟或迟滞改变边界。
- 仅在资格或识别结果发生变化时请求重判，处理原版房间清理、分配迁移与事件重入。持续效果按确认规则撤销／刷新，进行中的生产与治疗按各自规则处理。
- 不让一个房间的环境异常修改全局阈值；空集合、无效格和异常温度不按零值自动通过。记录房间类型、世界、位置与失败项，限频输出。

### 4.4 效果与进度结算

- 为每种效果记录来源、目标、开始／结束条件与撤销方式。重复房间更新或读档不得叠加同一来源的修正。
- 原版房间升级后，检查附属建筑的 `RoomTracker`、分配和原版效果是否仍满足要求；只兼容确认的升级关系，不全局把所有高级房间判作任意原版房间。
- 生产修正在真实进度入口生效。暂停保留批次和进度，恢复不重复投料；一次完成仍只结算一次产出。连续设备是否同时改投入、产出及能耗须按 D09 契约实现，不直接修改全局配方时间。
- 娱乐效果分别处理普通复制人和指定特质；共用统一触发契约，取消任务不能冒充成功使用。附加士气不得意外覆盖原版设施已授予的独立效果。
- 治疗速度与疾病治愈分开。医疗中心还需完成分配、活动范围和设施使用许可；辐射病救治成功时再按 D12 处理永久状态，避免保存／加载或取消导致重复惩罚。
- 科研与发射效果明确来源建筑、操作者和目标；跨世界、目标删除、换人、房间失效、发射后离开平台时按确认的生命周期重新校验，不每步遍历全部火箭／喷泉。

### 4.5 保存与兼容

| 数据 | 保存策略 |
| --- | --- |
| 平均环境、cavity 缓存、候选名单 | 派生状态，不保存；加载后由有效格和设施重建 |
| 房间类型、升级关系、设施名单 | 配置状态，初始化幂等登记；不把配置副本写入每个存档对象 |
| 有时限的士气／压力／属性效果 | 优先复用原版可保存的 Effect；核实实际序列化与重复加载行为 |
| 隔离开关、病人归属、治疗进度、救治成功标记与永久后遗症 | 仅保存 D11、D12 确认后确有需要且原版未保存的字段，使用稳定对象引用；读档校验目标仍存在 |
| 科研／火箭／物流的跨阶段效果 | 依据 D14、D15 只保存需要跨阶段保留的来源、目标和状态，不把重建临时列表当作已结算记录 |

DLC 必须按实际资源和 `GetRequiredDlcIds` 核实，不凭中文名判断；已确认数据挖掘中心需要 `DLC3`、群星航天指挥站需要 `EXPANSION1`。缺失 DLC 正常跳过对应内容；已支持版本的关键补丁签名不匹配须说明具体未生效模块，不只留下“登记完成”日志。其他 Mod 新增的建筑、材料或房间不自动纳入白名单。

### 4.6 房间独立构建

延续 [[系统隔离验证记录]] 的各系统独立验证要求。实施时新增房间模式（建议名 `Room`），同步工程条件、`BuildProfile`、入口、本地化筛选、包清单、构建／部署脚本和实际 DLL 检查。房间独立版只编入房间、房间所需的材料装饰度和公共入口，不能顺带带入工业过热／建材扩展或电力损耗。

反向检查同样必要：新增房间源码不能因 SDK 默认包含 `.cs` 而漏入 Industrial／Power；Combined 是否纳入房间须按整合阶段范围明确选择。现有脚本不支持 `Room`，**本轮不提供可执行的房间打包／部署命令**。房间独立版发布号、切换存档策略和整合发布号在实施时确认，不借用电力 `0.0.2` 自动发布。
