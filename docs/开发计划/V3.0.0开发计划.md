# V3.0.0 开发计划：房间系统

编写日期：2026-10-19。设计依据：[[4. 房间系统设计]]，系统定位见 [[ONI Reform 总体设计#4. 房间系统]]。

**状态：P1 基础接入代码已落地，效果与游戏验收未完成。** 本轮已实现房间独立构建模式、房间类型登记、平均装饰度／平均温度条件、原版优先的冲突仲裁、两间原版房间改造、16 个新增房间的构成登记，以及纯判定层测试和验证包检查。房间效果（士气、压力、生产效率、医疗、科研、航天）尚未接入；大房间、环境和界面仍需游戏内验收。`V3.0.0` 沿用总体设计的系统里程碑名，不代表已确定房间独立版发布号，不修改现有版本元数据。

工作分支：`codex/room-system`，从 `codex/power-system` 的 `4c20bc6` 创建。该基线包含工业与电力代码及三种隔离构建；源码存在不代表应在房间独立验证时启用它们。当前工程接受 `Industrial`、`Power`、`Room`、`Combined`，默认 `Power`；房间独立模式已加入工程条件、`BuildProfile`、入口、本地化筛选和包检查脚本（见 §4.6）。已有交付见 [[V0.2.2开发计划]]、[[电力V0.0.2开发计划]] 和 [[系统隔离验证记录]]。

## 1. 目标与实施范围

让房间构成、平均装饰度和平均温度成为工程条件，提供分设计已列明的生活、娱乐、工业、医疗、科研及航天加成。保留 T1 开局体验，复用原版房间识别、建筑使用、属性效果与分配机制。

### 1.2 边界

- T1 的公共厕所、卫生间、宿舍、食堂不新增条件或改变加成；未列出改造规则的原版房间不顺带改数值。
- 不新增设施、配方、科技或整套特质生成系统；房间使用现有建筑。特质定义不足时先完成不依赖该定义的工作。
- 不改复制人周期装饰感知算法；房间环境是独立条件，不更改建筑本体温区、内置加热、强制运行、自动化、磨损或维修规则。
- 工业区不直接复用工业温控的 29 栋白名单作为已确认名单；原版「工业机械」标签与本设计的「工业建筑」是两种用途。
- 房间独立验证不启用工业或电力系统。整合阶段再验证既有系统交互；不提前加入辐射耗散系统。医疗中心的辐射病救治属于本篇明确列出的房间效果。


`KleiVersion`：`ChangeList=744825`、`BuildBranch=release`。参考代码仅用于 `rg` 定位；下表结论来自本机目标反编译结果。反编译临时文件位于忽略目录 `_build/room-doc-reference/`，不分发、不提交，不作为运行依赖。

| 入口 | 已核实行为 | 对实施的约束 |
| --- | --- | --- |
| `Db.Initialize()`、`Database.RoomTypes(ResourceSet)` | 初始化房间分类及类型，构造各房间的主条件、附加条件、升级路径和效果 | 在房间表存在、首次房间探测前登记；实施时核实补丁时序和幂等性，不在每次刷新重复登记 |
| `RoomType` 构造函数、`isSatisfactory(Room)` | 主条件不满足与附加条件不满足返回不同状态；构造函数同时接收 `priority`、`upgrade_paths`、`effects` 等 | 保留原版对象的 ID、未修改条件和升级关系；变更不可只修改显示文本 |

| `RoomTracker.IsInCorrectRoom()` | 比较 `room.roomType.Id == requiredRoomType`，不自动认可升级房间 | 地质研究室等升级款需要核对建筑原有房间许可；不能无条件放宽所有 `RoomTracker` |
| `RoomType.TriggerRoomEffects(...)` | 由主条件匹配的触发建筑把 `effects` 加到目标复制人 | 登记效果不等于会触发效果；需核实每种建筑的实际使用链和时机 |
| `RoomMonitor`、`CavityInfo.OnEnter(...)`、`ParkSign.TriggerRoomEffects(...)` | 复制人路径推进时发现房间变化，通知室内建筑；公园标识据此触发房间效果 | 可参考人造公园的进入触发，但房间重建时的静止复制人仍需复核，不能据此统一其他房间的触发方式 |

| `DecorMonitor.Instance` | 按时间累计感知装饰度，周期结算 | 房间判定不写入其累计值、不修改周期效果阈值；材料改动导致感知输入变化属于另需验证的实际结果 |
| `MissionControlClusterConfig`、`MissionControlCluster.Instance.UpdateWorkableRocketsInRange(...)` | 群星指挥站属 `EXPANSION1`，原版配置已有速度倍率；范围筛选使用半径常量值 | 须区别“新增加成”和“原版总效果”；仅改配置常量不保证改变已编译的调用 |
| `GeoTuner.Instance`、`GeoTunerConfig` | 保存分配的喷泉和调谐修正，要求 `RoomTracker`；配置有调谐数量上限 | 产量、数量限制、原版温度修正与 UI 要分别追踪，不能只修改一个静态值就称全部生效 |
| `DataMinerConfig.GetRequiredDlcIds()`、`DataMiner.ComputeWorkProgress(...)` | 数据挖掘中心依赖 `DLC3`；进度已有按建筑本体温度计算的 `EfficiencyRate` | 房间低温与建筑自身效率是两个量；独立房间加成不能替换原版温度效率或重复推进进度 |

### 4.2 超过 128 格的房间

1. 保留工业区、航天发射场、星际货运站的既定尺寸，不为适应原版探测上限而缩小它们。
2. 先做大房间接入验证：核实运行期调优值能否在初始化前安全扩容，并配合新增类型自己的尺寸条件。不能只改 `MAXIMUM_SIZE` 条件；也不能只在候选判定时伪造内容，绕过原版建筑分配与事件。
3. 如果扩容会使无关区域创建额外普通房间、改变养殖拥挤度／房间显示或显著放大内容收集成本，则改为只识别明确候选区域的局部接入，并重新核实建筑／植物更新链。方案按证据选择，不对共享探测器无条件放宽全部房间规则。
4. 必须验证最小尺寸、原版 128 格边界、各房间设计上限及上限外一格；开放洞穴、跨世界、火箭内部和太空发射平台不得被误认。保留原版房间自身的大小条件。
5. 记录每次拓扑变化涉及的格子数与候选数，在专门测试档观测大殖民地开销。通过前不把“大房间支持”标为完成。

### 4.3 平均环境与动态重判

- 以 `CavityInfo.cells` 建立拓扑快照；环境缓存按世界、有效 cavity 及本次拓扑身份区分。读档后重新建立，不把旧房间对象或句柄永久序列化。
- 建筑增减、植物变化、作品／藏品替换等结构变化使相关区域失效；温度和装饰变化还需独立的环境更新渠道。不能认为原版建筑变更事件会覆盖气体温度变化。
- 先按 §3 的采样契约计算房间平均值，再统一提供给所有条件和显示。显示值不能采用另一套四舍五入后参与比较；摄氏显示与 K 存储只做一次一致换算。
- 对有环境条件的候选区域分批更新，避免每个模拟步全图扫描；同一轮一个区域最多计算一次共享快照。更新频率待确认，不用不可见的延迟或迟滞改变边界。
- 仅在资格或识别结果发生变化时请求重判，处理原版房间清理、分配迁移与事件重入。持续效果按确认规则撤销／刷新，进行中的生产与治疗按各自规则处理。
- 改造房间失效降级后仍要保留回升路径：私人卧室降级到卧室、宴会厅降级到大餐厅／食堂时，环境监控继续观察这些原版房间；否则装饰度或温度恢复后不会重新升回改造房间。降级目标集中记录在 `RoomDefinition.FallbackRoomIds`。
- 不让一个房间的环境异常修改全局阈值；空集合、无效格和异常温度不按零值自动通过。记录房间类型、世界、位置与失败项，限频输出。

### 4.4 效果与进度结算

- 为每种效果记录来源、目标、开始／结束条件与撤销方式。重复房间更新或读档不得叠加同一来源的修正。
- 原版房间升级后，检查附属建筑的 `RoomTracker`、分配和原版效果是否仍满足要求；只兼容确认的升级关系，不全局把所有高级房间判作任意原版房间。
- 生产修正在真实进度入口生效。暂停保留批次和进度，恢复不重复投料；一次完成仍只结算一次产出。连续设备是否同时改投入、产出及能耗须按 D09 契约实现，不直接修改全局配方时间。
- 娱乐效果分别处理普通复制人和指定特质；共用统一触发契约，取消任务不能冒充成功使用。附加士气不得意外覆盖原版设施已授予的独立效果。
- 房间详情显示已实装效果列表与工业区／数据机房生产效率行；原版房间改造通过追加 `display_details` 项显示新增效果，字段不可访问时只影响显示、不影响效果发放。
- 治疗速度与疾病治愈分开。医疗中心还需完成分配、活动范围和设施使用许可；辐射病救治成功时再按 D12 处理永久状态，避免保存／加载或取消导致重复惩罚。
- 科研与发射效果明确来源建筑、操作者和目标；跨世界、目标删除、换人、房间失效、发射后离开平台时按确认的生命周期重新校验，不每步遍历全部火箭／喷泉。

### 4.6 房间独立构建

延续 [[系统隔离验证记录]] 的各系统独立验证要求。已新增房间模式 `Room`，同步工程条件、`BuildProfile`（`RoomEnabled`）、入口日志、本地化筛选、包清单、构建／部署脚本和实际 DLL 检查。房间独立版只编入房间判断层、房间所需的材料装饰度与公共入口，不带入工业过热／建材扩展或电力损耗。

反向检查同样必要：房间源码不能因 SDK 默认包含 `.cs` 而漏入 Industrial／Power。工程已按模式排除：Power／Industrial 移除 `Rooms\**` 与房间服务文件；Room 移除工业、电力、加热、硬度、订单与温区目录，只保留房间与 `Temperatures`。Combined 纳入房间，补丁并集由 ProfileChecks 校验。

实际执行结果（2026-10-19）：

- `dotnet build ... -p:SystemProfile=Room` 以及 Industrial／Power／Combined 均构建成功，0 警告 0 错误。
- 本机没有 PowerShell 7，`build-profiles.ps1` 的 `#Requires -Version 7.0` 无法直接执行；脚本本身已加入 `Room` 模式、`roomEnabled` 清单字段、按 `STRINGS.ROOMS.MATERIALOVERHAUL.` 过滤 PO 的规则，以及 `--room-game` 契约检查，但**尚未在 PowerShell 7 下实际跑通**。
- 用等价的手工打包步骤生成四种验证包，并通过 `MaterialOverhaul.ProfileChecks`：Room 15 个房间补丁、98 条文本；四模式隔离检查 217 项全部通过。
- 新增 `ProfileChecks --room-game <Assembly-CSharp.dll>`：只读元数据核对 17 个补丁目标的方法签名，以及 `RoomType` 的三个私有自动属性字段（`additional_constraints`／`effects`／`display_details`），共 63 项通过；不加载游戏程序集，也不替代游戏内验收。
- 房间独立版发布号仍沿用工程版本 `0.2.2`，未自行升版；部署与存档策略未执行，需用户授权。
