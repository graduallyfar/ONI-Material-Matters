# v0.0.3 开发文档

本版目标：**让金属精炼器的「铝矿 → 铝」成为建筑系统的第一个完整可玩实例**。默认安装、不依赖 `debug_values.txt`，就能经历订单准备、锁定投料、预热、生产、温度暂停与恢复、控制模式补热、强制运行、材料硬度磨损、过热损坏、维修和保存读取，并能从界面理解当前条件。

> **实施状态（2026-10-11 追加）：代码已交付并通过构建与判断层测试；游戏内验收（§9.2）尚未运行。**
> 本节以下内容保持编写时的原样，实施记录、发现的差异与待用户决定项见文末 **§10**。

**文档状态：待开发。** 编写日期为 2026-10-11，代码审阅基线为本地提交 `32b5a7a`。本文交给 **deepseek harness** 执行代码任务；编写本文时没有修改源码、构建、部署或运行游戏。已有实现不等于游戏内已通过，以下任务和验收项均不能提前标为完成。

机制依据为 [[2. 建筑系统设计细节]]，总体方向见 [[ONI Reform 总体设计]]；前版记录见 [[V0.0.1开发计划]]、[[V0.0.2开发计划]]。用户已授权对未定数值先给出暂定值，本文将其集中列出；**暂定值可用于实现与验收，不代表最终平衡定案。**

# 1. 范围与现状

## 1.1 本版做什么

| 范围 | 交付要求 |
| --- | --- |
| 金属精炼器炼铝 | 完整接通温区、加热用电、生产、硬度、损坏、维修、界面与存档 |
| 订单 | 在金属精炼器上实现按笔查看、编辑和取消，支持重复配方与无限订单每轮额度；完成跨配方切换回归 |
| 默认配置 | 铝配方温区、金属精炼器硬度与磨损、加热数值均不依赖调试标记 |
| 游戏接入缺口 | 修复红信号下不能开始准备批次、温度停产仍占用复制人、暂停期间生产耗电与磨损等问题 |
| 验证 | 判断层回归、真实游戏验证清单与结果记录，明确尚未运行的场景 |

**不扩展**其他建筑的温区或硬度名单，不给其他金属配方补温区，不开发电线材料、电力系统革新、房间或辐射系统，不重做冷却液与产物热量算法，不引入自动制冷、预热超时换单或新的维修费用规则。

适用范围必须按机制分别限定：

- 温区、温度效率与内置加热：仅 `MetalRefinery` 上解析到的 `AluminumOre → Aluminum` 配方。
- 订单管理：金属精炼器整台建筑的配方队列，否则无法保证炼铝与其他订单切换。原有其他白名单建筑的订单行为不顺带重做。
- 过热阈值与要求硬度：属于**建筑级**规则。金属精炼器换成其他配方后仍受这两项材料规则影响，不能写成“其他配方所有行为完全原版”。其余配方仅不施加新增温区、温度效率和内置加热。
- 共享判断函数的修复可以复用，但新增游戏接入不能仅凭 `GetComponent<MaterialOverhaulFab>() != null` 就扩散到五个白名单建筑。

以下依据只读参考 `E:\ONI-Ref\Assembly-CSharp\Assembly-CSharp.decompiled.cs`，不声称它是网上最新版本。实现前由 harness 复核实际引用程序集的签名与版本。

| 原版入口 | 已读到的行为 | 本版约束 |
| --- | --- | --- |
| `MetalRefineryConfig.CreateBuildingDef/ConfigureBuildingTemplate` | 生产额定 1200 W，本体生产热 16 kW；`LiquidCooledRefinery`，复制人操作，冷却液要求 400 kg，普通精炼配方基础时间 40 s | 数量、时长以实际解析的配方为准；不把 40 s 当作任意工人、任意效率下的真实耗时 |

## 2.2 温度效率：完成指数分段

沿用总体设计的指数形式，用边界条件确定系数；无需再留待定函数。为避免绝对温度参与大指数，采用等价的归一化写法：

$$
\eta_T(T)=\begin{cases}
0.3^{(450-T)/150},&300\le T<450\\
1,&450\le T\le650\\
0.8^{(T-650)/150},&650<T\le800
\end{cases}
$$

此处 T 用 ℃便于阅读；代码使用 K 的温差归一化，结果相同。强制运行低于 300 ℃取 0.3、高于 800 ℃取 0.8。普通运行越界时禁止生产，不借效率为零代替停机处理。

验算点：375 ℃效率约 0.547723，725 ℃约 0.894427；300／450／650／800 ℃分别为 0.3／1／1／0.8。温度效率乘到原版工人操作效率上，只改变进度速度，不改变投入与产出质量；同一操作过程只乘一次。

## 2.3 磨损与加热的数量检查

- 从零余额开始且硬度低于 25 时，连续实际生产 19 s 不扣整点生命，余额为 0.95 HP；再生产 1 s 扣 1 HP；硬度等于 25 时为零磨损。整数扣血门槛要处理浮点累计误差，不能因 0.2 s 分步使应扣的 1 HP 永远差一点。
- 若目标版本金属精炼器最大生命为 30 HP，则忽略其他伤害与维修，累计实际生产 600 s 后耗尽。该推算用于检查单位，不是新增生命值设置。
- 加热热量为 `Q(kJ) = P电(W) / 1000 × 1000 × dt(s)`。0.2 s 满额预热注入 240 kJ，补热 40 kJ；实际供电不成立时注入 0。
- 普通生产热 16 kW 与上述加热热量独立，只在原版真实生产活动成立时保留；配方完成给冷却液的热量仍由原版结算一次。

# 3. 批次、温控和生产状态

## 3.1 三件事分别判断

1. **批次准备**：从有序订单选择原料与冷却液齐备的一笔，锁定订单身份、配方和本批材料。红信号不能阻止订单需求、取料、锁定；准备不推进生产，不结算产物。
2. **加热许可与意图**：有有效批次、材料已锁定、手动启用、建筑未损坏停机，按模式与本体温度提出电力需求；实际有电才注热。无需复制人，自动化红信号也可加热。
3. **真实生产**：有效批次 + 温控状态允许 + 原版供电、自动化、操作工、管道等非温度条件。只有实际推进时才产生生产电耗、生产热和机械磨损。

加热状态不要命名成 `productionRunning` 后拿温度许可代填。界面、耗电与磨损共享真实状态事实，避免“允许生产”被显示为“正在生产”。

## 3.2 普通运行状态与边界

| 情况 | 生产行为 | 加热行为 |
| --- | --- | --- |
| 新批次或低温停机后，默认模式低于 315 ℃ | 保留批次，禁止操作 | 预热到 315 ℃ |
| 默认启动条件已满足，300–800 ℃ | 按温度效率生产 | 不补热 |
| 默认模式跌破 300 ℃ | 暂停，重新等待 315 ℃ | 预热 |
| 新批次或低温停机后，控制模式低于 470 ℃ | 保留批次，禁止操作 | 预热到 470 ℃ |
| 控制启动条件已满足，450–650 ℃ | 按温度条件允许生产 | 按 460／470 ℃回差补热 |
| 控制模式跌破 450 ℃ | 暂停，重新等待 470 ℃ | 预热 |
| 默认超过 800 ℃／控制超过 650 ℃ | 高温暂停，达到 785／640 ℃恢复线后再检查所有条件 | 关闭普通加热 |
| 没有批次、全部缺料 | 不生产 | 不加热，无有效温区目标 |

启动线不是每个模拟步都替代工作下限：默认已经开工后在 305 ℃仍能生产，控制已经开工后在 455 ℃仍能生产并补热。初始化或模式切换时若温度已经高于对应启动线且不在高温等待中，可直接通过启动条件；**470 ℃已达到但还在等操作工，不应被当成从未预热完成。**

保存启动资格、高温暂停原因及补热回差状态。读档后重读温度与运行条件；若保存时处于回差带，不能无条件清掉原加热状态。低温和高温恢复需同时校验，例如外部骤冷直接从 810 ℃降到 290 ℃应预热，不能仅因低于 785 ℃就恢复生产。

温度暂停必须：保存本批进度与原料、撤销操作任务并释放复制人、停止生产活动与生产热、不轮换订单。恢复只重建操作任务，不调用取消／重新结算。用实际 `WorkTimeRemaining` 核对暂停前进度，避免原版 `OrderProgress` 更新时序造成丢失最后一步。

## 3.3 强制与模式切换

- 强制运行是独立开关，覆盖温区和启动等待，持续加热并按 §2.2 的效率生产；无批次不加热，红信号不生产，有电且手动启用且未损坏才加热。
- 强制期间保留原先默认／控制模式。关闭时立即恢复对应普通判断，不清批次、磨损或原因；低温先预热，高温进入等待，正常温区按对应启动资格处理。
- 默认／控制切换保留批次与进度，按新模式重新建立启动／恢复条件和加热意图；旧目标与旧绿信号不能留到下一批。
- 生命值耗尽仍按原版损坏停机；过热但尚未损坏停机时，强制开关不阻止原版过热伤害，也不免除材料相变。

## 3.4 自动化输出

仅当**已锁定铝批次**且本体在 450–650 ℃（含端点）时输出绿，其余红。红色输入、等操作工、断电或损坏不会把已经符合该温区条件的输出强制变红；输出只报告温区。无批次、无温区配方或取消后无新批次时输出红。

保留已有端口 ID 与布局，核对端口说明、叠层显示及新旧存档。不能把温区输出当作批次准备／加热的前置许可，否则接成反馈回路后冷机无法启动。

# 4. 加热接入实际电网

## 4.1 必须达到的耗电矩阵

下表以原版生产功率 1200 W 且电力供应足够为前提；无生产时不收生产部分。

| 实际状态 | 生产 W | 加热 W | 合计 W | Mod 注热 kW |
| --- | --- | --- | --- | --- |
| 空闲／无有效批次 | 0 | 0 | 0 | 0 |
| 单独预热 | 0 | 1200 | 1200 | 1200 |
| 生产，无加热 | 1200 | 0 | 1200 | 0 |
| 控制生产并补热 | 1200 | 200 | 1400 | 200 |
| 红信号或等工人，仍需补热 | 0 | 200 | 200 | 200 |
| 强制生产并持续加热 | 1200 | 1200 | 2400 | 1200 |
| 强制但生产被红信号暂停／等工人 | 0 | 1200 | 1200 | 1200 |
| 高温等待，无强制 | 0 | 0 | 0 | 0 |
| 断电、手动禁用或损坏停机 | 0 | 0 | 0 | 0 |

“需要加热”和“正在加热”必须分别可识别。电路需求可在未获供电时存在，但不能因此提前注热；不能为了不耗电先把需求清零，导致来电后永远不再请求。

## 4.2 建议接入方式与验证边界

优先保留建筑原有电力连接，针对目标实例为电力需求和实际消费提供生产／加热合计。核对 `EnergyConsumer`、`CircuitManager`、`Operational` 的调用时序后选择有限补丁或专用供电组件；**本文不把尚未实现验证的电网方案说成已可用。** 如需额外消费者，必须证明不重复登记、不产生第二个可见接线口，清理时正确注销。

不得单纯 `Operational.SetActive(true)` 来给预热扣电：原版动画和 16 kW 生产热会一并启动。也不得只改界面功率，或在实际供电没有确认时用 `IsConnected` 代替供电许可。

本版采用整机当前需求统一供电，不新增“供电不足先牺牲补热”的部分供电优先级。断供后停止真实生产与注热，保留未满足的需求并等待电网恢复；在 1200→1400→2400 W 切换、缺电恢复时核对事件顺序，避免免费注热或卡死。

热量仍走 `GameComps.StructureTemperatures.ProduceEnergy`，温升由 SIM 根据原版有效热容与换热计算。普通目标封顶仅限本次 Mod 注热，不能拦截环境升温或原版生产热。无配方、取消或切换到无温区配方时同时清掉加热需求和意图。

# 5. 订单、存储和存档

## 5.1 最小可用的逐笔订单界面

金属精炼器保留原版配方选择与配方详情，补充**按添加顺序排列的订单列表**。每行包含配方、有限剩余／无限本轮进度、当前批次标记、编辑与取消入口。新增订单总是追加到末尾，同配方可重复。

- 有限数量与无限额度按订单身份编辑，不再按 recipe id 合并全部同配方订单。有限剩余数量口径包含当前尚未完成的一批；调低到 0 即按取消处理。
- 无限订单默认每轮 1 批，支持 1–99。修改额度时保留已完成数；若新额度已用完，在当前已锁定批次结束后让出，无当前批次则直接让出，不抢先取消当前批次。
- 原版按配方合计的数量用于兼容与汇总，不得与逐笔列表成为两套相互覆盖的编辑源。明确调整或禁用金属精炼器上有歧义的合计数量／∞写入入口，不能保留“输入数量悄悄合并重复订单”。
- 暂不要求拖拽排序、订单模板或跨建筑调度。不引入 PLib 仅为实现本版界面。

## 5.2 调度不变量

1. 批次准备前按订单顺序检查原料与冷却液，选中后锁定**具体订单身份**；推荐持久化单调编号，不能只用 recipe id 或会移动的数组下标。
2. 当前批次未完成／取消前，温度暂停、后续增删、其他原料送达都不抢占。有限订单材料齐备时连续做剩余批次；无限订单完成额度才让出，中途缺料保留本轮进度。
3. 下一生产预告必须使用无副作用查询，不能复用会修改 cursor 的 `SelectNext`。实际生产中的下一项扫描也不能提前改变有限订单连续执行的归属。
4. 原版配方计数字典只是订单表的投影。完成过程只扣一次 Mod 订单，只让原版结算一次；不得在完成前缀与原版正文之间被旧计数重新导入已删除订单。
5. 取消精确对应那一笔。即使队列里仍有相同配方，也必须能取消当前笔并退回其批次原料；不能仅靠原版 `IsRecipeQueued(recipe)` 作为取消依据。
6. 全部缺料时等待存储／订单等变化，禁止每 200 ms 或每秒无条件整表轮询；稳定数据缓存，失效时再计算。

按本地原版 `UpdateOpenOrders`，预取覆盖多配方并合并材料。**本版沿用每配方最多预取 2 批的上限**，不一次搬齐无限需求；保证所有排队配方都进入需求计算，重复配方按合计扣除可用量，红信号下仍可准备。已在加工仓的矿石与冷却液只归当前批次，不能同时算成下一批可用。

## 5.3 读档必须恢复同一批次

| 数据 | 归属与恢复要求 |
| --- | --- |
| 订单身份、顺序、剩余、无限额度与本轮进度、cursor | Mod 保存；同配方不同笔不得混淆 |
| 当前批次关联订单、配方与阶段 | Mod 保存；恢复时验证配方仍存在且匹配建筑 |
| 原料实物、输入／加工／输出仓 | 原版存储拥有；不得复制一份物品或质量记录用于再生成 |
| 当前生产进度 | 以原版实际剩余工作量为依据恢复；需要快照时只保存一个明确同步的权威值 |
| 模式、强制、启动资格、高温等待、补热回差 | Mod 保存；读档后校验实际条件，不能无条件重新预热或清掉回差 |
| 磨损余量、当前尚未修复原因、强制过热附加的机械显示原因 | Mod 保存；原因和小数均不能读档重置 |
| 温区、硬度、过热规则、端口输出、组件引用 | 由配置与实际对象重建，引用不序列化；重建完成前不生产、不注热 |

处理原版 `OnSpawn` 退回加工仓的步骤时，只对目标建筑使用范围明确的恢复流程：可保留并正确识别加工仓，或在原版退回后优先恢复已保存的同一批次。两种方式都必须先阻止其他订单抢占／丢弃材料，再恰好恢复一批；具体钩子在目标版本核实。不能靠重新选择任意同配方订单完成迁移。

新建存档、原版存档及 v0.0.2 升级分别测试。旧版未保存的信息不能伪造：尽量使用 `lastWorkingRecipe`、进度与存储恢复；同配方身份无法唯一还原时按固定顺序选定并记录一次迁移日志，保住实物、数量和可恢复进度。旧伤害原因缺失时明确标为迁移未知，不能猜成纯机械而阻止原版过热维修；只对未知来源的旧损伤保留原版维修温度行为，新产生的明确原因按本版规则处理。

异常配方／缺失 DLC 不抛异常，不结算虚构产物；停止该无效批次的加热，保存或按原版安全返回仍存在的材料，日志说明无法恢复的字段。旧版已经丢失的信息无法通过本次升级保证完全恢复，但本版新存档必须完整往返。

# 6. 硬度、损坏与维修

## 6.1 常规配置与准确计时

默认仅登记 `MetalRefinery` 要求硬度 25，读取主建造材料 `PrimaryElement.Element.hardness`。低于要求允许生产并按 §2 数值磨损，达到或超过不机械扣血。

实际生产秒数使用**确实推进工作的模拟时间**，而不是“等效满效率工作量”。例如效率 0.3 下实际工作 20 s 仍扣 1 HP，因此低效完成同一批需要更久、磨损更多。接入应核对本步生产前后状态／剩余工作量，只在确实工作的一段时间累计；完成的最后一帧不能漏计或算两次。

复制人和非复制人路径不能重复累计。预热、补热但未生产、等待工人、红信号、断电、温度暂停、维修和损坏停机不累计。维修实际占用期间按维修状态停计，不能仅凭 HP 未满就把所有正常生产时间排除。

修正整数换算：不能取走所有整数磨损再把 `wear × 0.05` 向下取整而丢余额。可在伤害余额中累计浮点 HP，或按已扣整数伤害反推消耗的磨损；每次累计、扣除、恢复后同步序列化字段。暂停、取消、换模式、换订单和维修不能顺带抹掉尚未扣出的余额。

## 6.2 当前未修复原因

- 首次实际机械扣血时就记录机械原因，不等到 HP 耗尽；轻微磨损与损坏停机用不同状态文字。
- 普通运行按实际机械／过热来源记录。当前仅超过阈值时显示过热条件，不把尚未产生伤害的状态一概称为“已受损”；实际过热事件／扣血来源应核对原版入口。
- 已机械损坏停机后，因原版免伤状态不再发伤害，仍按本体超过过热阈值追加过热原因，不能再扣 HP。
- **在强制运行时发生过热损坏**，锁存过热原因和附加的机械显示原因，即使材料硬度合格也显示两种；附加显示不制造机械伤害。
- 关闭强制、降温、换订单或读档不会清除已有原因。不能使用“当前 forced && 曾过热”每次临时计算历史原因，也不能在普通过热已经结束后仅切开关就伪造一次强制过热事件。

## 6.3 维修时序

沿用原版维修触发、耗材与工作流程。纯机械原因在原版 `ResetTemperature` 调用处阻止重置；含过热时放行原版重置，不在刚过热时主动降到室温。

核对 `BuildingPartiallyRepaired` 的订阅执行顺序：用于判断本次维修的原因必须保持到温度重置决策之后，再在确认完全修好时清除。本体之后仍过热、再受损时开启新的未修复原因状态。完全修复清除原因，不清除机械磨损的小数余额。

状态项不应通过替换 Main 类别把原版断电、缺料或其他关键状态遮掉；机械和过热两种原因能同时看见。

# 9. 验证清单与完成定义

## 9.1 自动检查重点

| 组 | 必测行为 |

## 10.3 实现上的关键决定（与文档口径的对应）

1. **温度暂停用「撤销操作任务」实现**，不是把效率乘零。已核实：`ComplexFabricator.Sim200ms` 按 `HasWorkingOrder && HasWorker` 设 `Operational.SetActive`，而 16 kW 生产热与生产电耗都读该活动状态；只改效率会让复制人继续被占用、生产热照发。本版在温度不允许时调用原版私有 `CancelChore()`，并在 `EnforceProductionGate` 里显式 `SetActive(false)`；批次、原料与进度全部保留（`ComplexFabricatorWorkable.resetProgressOnStop` 为 false，`CreateWorkChore(choreType, orderProgress)` 会按进度重建）。
2. **磨损按真实时间计**。已核实 `WorkChore.StatesInstance.Update` 先算 `dt2 = dt × GetEfficiencyMultiplier(worker)` 再调用 `Workable.WorkTick`／`OnWorkTick`，因此本 Mod 记录最终倍率，用它把回调收到的 dt 还原成真实秒数（`DamageConversion.RealProductionSeconds`）。非复制人路径的 `ComputeWorkProgress` 收到的本来就是真实 dt，两条路径互斥，不会重复累计。
3. **伤害余额以 HP 累计、取整带浮点容差**（`WearAccumulator`）。0.2 s 分步累计 100 次若直接用 float 求和会得到 0.99999934，差一点永远扣不出 1 HP；改为 double 累计 + 1e-6 容差，扣除仍是精确减整数，余额不会漂移（测试已覆盖）。
4. **电网需求与实际消费分开**。`EnergyConsumer.WattsUsed` 返回**需求**（原版同样返回额定值，由电路决定供不供得上），`WattsNeededWhenActive` 取原版额定与本 Mod 需求的较大者；只有 `IsPowered` 为真时才真正注热。断电时需求保留，避免「为了不耗电先把需求清零，来电后不再请求」。
5. **过热「条件」与「已受损」分开**。过热原因在实际过热扣血事件上锁存（`BuildingHP.OnDoBuildingDamage` 后置 + 本 Mod 机械伤害标记区分来源），不再只凭超过阈值就写「已过热受损」；损坏停机后原版进入免伤状态、不再发伤害事件，这时才按阈值兜底追加原因。强制运行期间发生的过热损坏额外锁存一条「附加机械显示原因」，只影响显示，不额外扣血。
6. **普通加热按目标封顶、强制不封顶**。预热／补热用「剩余所需热量 =（目标温度 − 当前温度）× 原版有效热容」限制末步注热，温升仍交给 SIM；不直接设目标温度。
7. **订单身份与配方标识分离**。同配方的多笔订单靠单调编号区分；读档按身份恢复当前批次；预告查询用无副作用入口，不复用会移动指针的 `SelectNext`。
8. **加热范围显式限制**。新增 `Zones/HeatingScope.cs`，内置加热与加热用电只对名单内建筑（本版仅 `MetalRefinery`）生效，不因「挂上了本 Mod 组件」就扩散到五个白名单建筑。
